## 1. What the MVP proves

1. **Routing to the right region.** A request reaches the server pinned to
   the region of its database: `/eu` in Frankfurt, `/us` in Ohio.
2. **A distinct database connection per routed system.** A route can hand
   the container its own database, which is what dedicated databases and
   customer-owned databases need later.
3. **Database migrations as a release step.** Every database is migrated
   before a deployment takes traffic, and a rollback stays safe.
4. **Observability.** Logs, traces and metrics of every region land in one
   place, with the region, the deployment and the system on every record.
5. **A well-built project structure.** One `vercel.json` describes the
   services, their placement, their routes and their bindings, and adding a
   region or a system is a small, reviewable change.
6. **One cloud console.** One console signs in once at the home and works
   with projects in every region, through the control plane.

## 2. Routing: path prefixes on one host, and why

The regions live under path prefixes of one host (`/eu`, `/us`, the home at
the root), not on hosts of their own. Host routing works on Vercel (a
`has: host` condition on a service rewrite; the spike's first shape used
it), and the regions moved under paths for four reasons:

- **The session.** The home's session cookie is host-only. On one host the
  browser sends it with every call to `/eu` and `/us`, and a region asks the
  home about it, so one sign-in covers every region today. With a host per
  region the browser would never send the cookie there, and the regions
  would first need tokens from the home (auth plan phase 1), which is
  product work.
- **`vercel.app` is a public suffix.** No cookie can span two `vercel.app`
  hosts, so on a Vercel domain a host per region cannot share a session at
  all. Only a custom domain changes that.
- **One origin.** The console calls `/eu` and `/us` without CORS.
- **Paths route anywhere.** A path rule needs no DNS and no certificate,
  which is how a dedicated system can live at `/sys/<name>` on the same
  host; the routing POC proved path rules next to host rules.

The cost is that the region is part of the API base URL (`https://<host>/eu`).
Moving a customer to a system of their own gives them a new base
(`/sys/<name>`), with paths or with hosts alike. Hosts per region, with
tokens and a custom domain, stay the product's later choice (auth plan
phases 1 and 5).

### P1. A distinct database per system

**Step 1, a static system** (about a day, no server change). A service
`system_acme` gets the same image, region `fra1`, the path `/sys/acme`, and
`CLOUD_DATABASE_KEY=ACME` in its environment, so the launcher serves from
`CLOUD_DATABASE_URL_ACME`, a database of its own (a small PlanetScale
database, or a schema of its own on the Frankfurt database for the first
run). The `migrate` step migrates it with the others, since it migrates
every `CLOUD_DATABASE_URL_<KEY>`. The home lists it as a region, so the
console can create projects in it. Done when a project created under
`/sys/acme` exists only in that database. The limits show why this is
step 1 only: every new system is a deployment, every function receives
every system's database address in its environment (the launcher drops the
others before the server starts), and a deployment holds at most 100
services.

**Step 1 passed on 2026-10-10** (deployment
`nextgen-preview-cloud-gpukezov4`): `system_acme` serves `/sys/acme` from
fra1 out of the schema `sys_acme`, the build migrated it with the other
databases, the console and the control plane list it as a region, and a
project created under `/sys/acme` answers there with its own secret while
`/eu` and `/us` refuse that secret, as `/sys/acme` refuses the EU
project's. Published project routing rules also reach preview deployment
URLs (a probe rule sent `/sys/probe/readyz` to the EU server on a preview),
so step 2 can run on this branch's previews.

**Step 2, the address from the route** (4–6 days, the systems concept's
layer 3). A project routing rule per system, added through Vercel's API
without a deployment, sends `/sys/<name>` to the regional server and sets
`x-nextgen-system` to a sealed envelope: the database address encrypted to
the master key the server already holds. The server opens it, checks that
the system's placement is its own region, and serves the request from a
connection pool per database (two to four connections each, idle pools
closed). A new system needs its database migrated and bootstrapped once
before its rule goes live; the launcher's migrate mode runs against the
envelope's address for that. Done when two systems on one server, added
without a deployment, each see only their own database, and a forged
header is refused.

**Step 2 passed on 2026-10-10** (deployment
`nextgen-preview-cloud-bx7xq70mo`, routing rule version `eb1174a1`).
`cmd/server/systems.go` builds an app per system on its first request: the
same services, caches, pool and background jobs the server builds for its
own database, keyed by system and address, at most 16 per instance and
closed after ten idle minutes. Not a pool per system inside one app,
because the signing key cache is keyed by project id and the platform
project's id repeats in every database. The envelope opens with the master
keys the server already holds, outcomes cached by the ciphertext's hash;
the header is removed before the app sees it; a refusal answers 400 and
never falls back to the shared database. The launcher turns systems on in
every region with its Vercel region as placement, and `launcher seal
<system> <placement>` seals an address from stdin with the same master key
variables. Onboarding was by hand: the launcher's migrate mode against the
system's direct address, `launcher seal` for the pooled address with two
connections, a routing rule through Vercel's API (`/sys/<name>/:path*` to
`/eu/:path`, setting the header), published. Results:

- `beta` and `gamma` answer through rules added without a deployment,
  served by the EU server from schemas of their own.
- A project created in each system, in `acme` and in the EU region answers
  only where it was created: sixteen checks, a clean diagonal.
- A forged header gets 400; `beta`'s envelope sent to the US server gets
  400, since it names fra1; the log says why, never the value.
- Opening a system took 35–190 ms per instance, its bootstrap included.
  An envelope is about 1.3 KB.

Two caveats for the product: a rule may only point at a server that
understands envelopes, since an older one ignores the header and serves the
shared database; and a system's migrations run outside the build, here by
hand, later from the control plane.

### P2. Observability

**The code side is done; where the data goes is the team's choice.**

- A system request's log lines carry `system=<name>`, never the address:
  the router puts the name on the request's logger. On a preview, the lines
  of `beta`'s and `gamma`'s requests name them and the EU's own carry none.
- The launcher stamps the server's OpenTelemetry resource with
  `service.namespace`, `cloud.provider`, `cloud.region`, `deployment.id`,
  `deployment.environment.name` and the service's role
  (`OTEL_RESOURCE_ATTRIBUTES`, an operator's own attributes after them).
- The control plane logs every create with the region's request ids for
  its three calls (`region_requests`). A server mints its own id per
  request and returns it as `X-Request-Id`, so the control plane's line
  leads into the region's log.
- Exporters flush at `SIGTERM`, which containers receive.
- Vercel attaches a container's output to every request in flight on its
  instance, so the server's `request_id` is what ties a request's lines
  together.
- **Left, because it needs a choice:** the backend. Vercel Drains (Pro,
  $0.50 per GB, runtime logs and Vercel's traces) and the server's own
  exporters (`NEXTGEN_INSTRUMENTATION_TRACE_EXPORTER_*` and its metric and
  log siblings, OTLP or Google Cloud) both point at it; scraping is not an
  option, since no instance is addressable from outside. A drain is
  standing configuration that sends data to a third party, so it waits for
  the team's choice. Then one dashboard (latency, errors, pool use per
  region and system) and one alert.

### P3. Migrations, end to end

**Passed on 2026-10-10.**

- **The control plane migrates in the build.** `api migrate` runs in the
  `migrate` service's build step after `launcher migrate`, and refuses
  production from any branch but main. A serving instance only reads its
  schema's version through its pool and refuses to start on an older schema;
  a newer one is fine. The first try failed because a plain connection
  handed the pooled address's `pool_max_conns` to PgBouncer as a startup
  parameter; the check now runs through the pool.
- **A failing migration stops the deployment.** A build with the US
  migrator pointed at nothing failed at the migrate step and the deployment
  ended in an error state without going live. The databases migrate one
  after another in key order, so those before the failure (here `acme`) are
  migrated and the rest are not, which expand and contract makes harmless.
- **A rollback across a migration holds**, rehearsed locally on the
  throwaway schema `rb_drill` of the EU preview database. A newer launcher
  with one extra additive migration migrated it (50 tables against 49
  elsewhere). The current launcher's migrate step on that schema was a
  no-op, which is what redeploying the previous commit does. The current
  launcher then served it, readiness, a project created and read back,
  which is what Instant Rollback does. goose skips database versions its
  files do not know and only refuses an unapplied file older than the
  database's latest, so migration numbers must stay in order across merges.
- **Systems.** Static systems migrate in the `migrate` step (`acme`).
  Dynamic ones were migrated by hand with the launcher's migrate mode; the
  control plane takes that over when systems become a product.

### P4. Project structure

**Done, with one decision left to Florian.**

- `apps/cloud/README.md` has the services table: what each service runs,
  where, under which path, on which database, and what it binds. A new
  region or static system is a service, a case in `build-output.sh` and its
  addresses in the project's environment; a dynamic system is a routing
  rule.
- `apps/cloud/scripts/deploy-preview.sh` deploys the working tree as a
  preview, with the preview schema and the alias as the servers' host, and
  points the branch's stable alias at it (`nextgen-home.vercel.app` by
  default).
- `vercel.ts`, generating the services from one table of placements, is
  not worth it at four services; it is once systems multiply.
- The routing POC (`apps/cloud/routing-poc/` and its Vercel project
  `nextgen-routing-poc`) is still there: P1 covers what it proved, and
  deleting the project is Florian's call.

### P5. One console through the control plane

**Done in code; one signed-in check left.**

- The console creates a project through the control plane
  (`POST /cloud/projects`), which makes the region's calls over its binding
  and records the placement. A home without a control plane answers 404
  there, and the console then calls the region itself as before.
- Listing stays with the regions. The control plane's placements know who
  created a project; the regions know who has access through teams. The
  regions' lists stay the truth until the directory learns team access,
  which is the auth plan's work.
- The console's tests pass, including the control plane path and the
  fallback on the projects screen.
- Left: one create in the browser by a signed-in person. It also closes
  the containers plan's last open check (T6, the control plane reaching a
  region over its binding).

## 7. Not in this proof

- **Product work:** teams across regions and home tokens (auth plan phases
  1–3), platform roles for support, billing, customer onboarding.
- **Before real customers:** production databases with backups and a
  rehearsed restore, a custom domain with hosts per region if the product
  wants them, rate limits and quotas, the legal documents, and background
  work on a tick (a cron per region calling an internal endpoint), since
  production instances scale in after five idle minutes.
- **Rolling out a version** to a share of traffic: Vercel's Rolling Releases
  do that for the whole deployment on Pro, with no code.
- **Versions per customer.** Flags decide who gets which version; routing
  rules carry it out. Reading a flag on every API request is billed per
  request ($0.03 per 1,000) and needs a JavaScript middleware in front of a
  Go server, and in a shared region every version runs against one schema,
  so a version per customer there can only be a short canary. A pin needs
  the customer's own database, which is what P1 prepares.
- **Customer-owned databases inside a customer's network.** They usually
  need static egress addresses or private networking, which Vercel does
  not offer for custom container images today.
