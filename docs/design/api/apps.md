## Goal

The identity model settled that an app is one document holding every config
it has, written in one call, declared in the release when the developer owns
it and registered through the API when someone else does. This note decides
what the document holds, how it is stored, how a release carries it, and how
the authorization server finds a client or an API in it.

## The document

An app has a `slug`, a `name`, an optional `preset` label and one array per
config kind. Each config kind has its own JSON Schema, written once in the
OpenAPI YAML and generated by the meta-schema pipeline, so the server, the API
and `.zitadel/meta/` share one shape:

| Schema | Holds |
| --- | --- |
| [`app.json`](../../../api/openapi/endpoints/schemas/app.yaml) | `slug`, `name`, `preset`, `clients`, `apis`, `registration` |
| [`app-client.json`](../../../api/openapi/endpoints/schemas/app-client.yaml) | One OAuth or OIDC client |
| [`app-api.json`](../../../api/openapi/endpoints/schemas/app-api.yaml) | One API the app serves, MCP servers among them |
| [`app-registration.json`](../../../api/openapi/endpoints/schemas/app-registration.yaml) | Whether clients may register into the app |

`saml` and `scim` join as kinds once their engines exist (below): nothing is
selectable without an implementation behind it.

```json
{
  "slug": "shop",
  "name": "Shop",
  "preset": "web",
  "clients": [
    { "slug": "web", "type": "confidential", "secret": "${{ SHOP_WEB_CLIENT_SECRET }}",
      "grants": ["authorization_code", "refresh_token"],
      "redirect_uris": ["https://shop.example.com/callback"],
      "apis": [{ "api": "orders" }, { "api": "billing/invoices", "scopes": ["invoices.read"] }] },
    { "slug": "desktop", "client_id": "ShopDesktop", "type": "public",
      "grants": ["authorization_code", "refresh_token"],
      "redirect_uris": ["http://127.0.0.1/callback"] },
    { "slug": "repricer", "type": "confidential", "secret": "${{ SHOP_REPRICER_CLIENT_SECRET }}",
      "grants": ["client_credentials"],
      "apis": [{ "api": "orders", "scopes": ["orders.write"] }] }
  ],
  "apis": [
    { "slug": "orders", "identifier": "https://api.shop.example.com",
      "scopes": [{ "name": "orders.read", "description": "Read your orders" }, { "name": "orders.write" }] },
    { "slug": "mcp", "identifier": "https://shop.example.com/mcp", "third_party": true }
  ],
  "registration": { "client_id_metadata_documents": true }
}
```

- **A slug names one config of the app**, across clients and APIs, so
  `shop/web` is unambiguous wherever another document or the console names it.
- **Clients speak the protocol's words** (`type`, `auth_method`, `grants`,
  `redirect_uris`), and presets fill them. There is no per-client
  `protocol: oidc|oauth`: OIDC is OAuth plus the `openid` scope, and a second
  field could only disagree with it.
- **A public client** holds no secret, authenticates with `none` and cannot
  use `client_credentials`. **A confidential client with
  `client_credentials` is a principal**: its tokens have the client as `sub`.
  What it may do is a grant on that principal, which the identity model's
  open question 2 decides; the document holds no rights.
- **A client lists the APIs it may call**, its default first: an API of its
  own app by slug, another app's as `<app>/<api>`. `scopes` narrows the API's
  scopes; leaving it out allows all of them. A same-app reference is checked
  when the document is written. Another app's is resolved when a request
  names it, so no write waits for another app to exist.
- **An API is an identifier, scopes and `third_party`.** The identifier is the
  `aud` of every token for it (RFC 8707): https, loopback http, or a `urn:`.
  No two apps in a project share one, and an app keeps every identifier it
  ever used, so a token minted for a retired API is never accepted by a new
  one.
- **Registration is switched on per app** (amends ADR 082 §9, which put it in
  `oauth.json`). A client that registers names no app; the app is the one
  whose API its first authorization request names as `resource`, and it may
  ask only for that app's `third_party` APIs, as the POC showed. The rule
  that open registration needs a login-only issuer stays project-wide.
- **Redirect URIs** are https, loopback http (any port, RFC 8252 §7.3), or a
  private-use scheme for a public client, without a fragment and in their
  canonical form, so the browser goes byte for byte to the URI that was
  checked ([POC findings](https://github.com/zitadel/nextgen/pull/2451)).
- **What the authorization server reads per request** (agreed with part A):
  the consent policy (`consent`: `skip`, which only a first-party client may
  use, `new_scopes` or `always`), `account_choice`, the display fields a
  client ID metadata document carries (`logo_uri`, `client_uri`, `policy_uri`,
  `tos_uri`, on the app), post-logout redirect URIs, `private_key_jwt` keys as
  a public JWK set (`jwks`), and a signing algorithm, RS256 unless the client
  (`id_token_signed_response_alg`) or the API (`signing_alg`) asks for ES256.
  Branding and flows find the app by its slug.
- **What the document does not hold:** token lifetimes and claim mappings,
  which are policies ([below](#lifetimes-and-claims-are-policies)), and a
  principal's rights, which are grants.

## Client ids and secrets

ADR 082 §3 had the server mint every `client_id`. It mints one only when the
document leaves it out:

- **A chosen `client_id` is kept**, for ids compiled into desktop and mobile
  apps (ownCloud, OpenCloud), ids a v4 or another identity provider issued,
  and ids every project a release ships to should share. Our own CLI's `cli`
  is the first case. It takes `[A-Za-z0-9._~@-]`, up to 255 characters: v4's
  ids contain `@` and import as they are, while a minted id never does.
- **Fixed for life.** A revision that leaves it out keeps it, one that
  changes it is refused (`app.field_immutable`), and a client removed and
  added back under its slug gets it again.
- **Unique in the project and never reused**, whichever app held it.
- **Minted ids are row ids** (`client_01K…`): the chosen value sits beside the
  row's own key, so no caller picks a primary key (ADR 047 §4). A chosen id in
  that form is refused, and so is one in a registration's form (`dcr_01K…`),
  so the shape of an id says where to look it up.

Secrets follow the app's writer:

| App | Secret |
| --- | --- |
| Declared | A `${{ NAME }}` variable the deployment froze (ADR 062, ADR 069), the developer's own value. A deploy is refused while the variable has no value |
| Registered | Generated by the server for each new confidential client, returned once, stored as SHA-256 (256 random bits need no slow hash). Or imported: a plaintext, or a hash passwap reads (v4's bcrypt, argon2, scrypt, pbkdf2), moved to SHA-256 the first time it matches |

A client may hold several secrets, so one can be rotated without downtime.
Generated secrets carry a `zcs_` prefix for secret scanners; the final format
is the [apps and machine identities note](https://github.com/zitadel/nextgen/pull/2430)'s
to decide.

## Scopes and audiences

- **An API's scopes are its own.** The built-in OpenID Connect scopes stay
  built in, and an API may not define them again.
- **Unknown is refused, never dropped.** A requested scope that is neither
  built in nor defined by the requested API is `invalid_scope`, and so is one
  the API defines but a first-party client's allowlist leaves out. A third
  party may ask for any scope of a `third_party` API, and the user's consent
  narrows what is granted.
- **Granted scopes are `scope`**, a space-separated claim (RFC 9068), never
  claims of their own. v4's project-audience scope
  (`urn:zitadel:iam:org:project:id:{id}:aud`) is an unknown scope.
- **One audience per token.** An access token's `aud` is the one API its
  request named; an ID token's `aud` is the client alone. v4 put the project
  and every client of the project in `aud`, which strict relying parties
  reject ([#9200](https://github.com/zitadel/zitadel/issues/9200),
  [#8055](https://github.com/zitadel/zitadel/issues/8055)).

The domain answers these rules
([`app.go`](../../../internal/domain/app.go): `AccessTo`, `GrantScopes`), so
the authorization server and anything else that issues tokens apply them the
same way.

## Kinds of data

Apps are configuration, whoever writes them: a declared app is code, a
registered one is configuration written through the API, revisioned like a
connection. Of the three kinds of data, the only stateful data is users;
transient data is sessions and consent; events are audit logs only. An app's
records fall like this:

| Record | Kind | Owner |
| --- | --- | --- |
| App documents and their revisions, client ids, API identifiers, a registered app's secret hashes | Configuration | Apps |
| Dynamically registered clients | Transient: purged once past a short lifetime of their own and named by no live consent | Apps stores them; the authorization server's `POST /register` writes them |
| Client ID metadata documents | Not stored: fetched and cached | Authorization server |
| Consents, codes, refresh tokens | Transient, stored like sessions | Authorization server |
| SCIM sync state | Transient: a reconcile rebuilds it | Apps (designed) |
| `app.*` events | Events: audit only, never a feed for an engine | Apps |

## Storage

Apps are stored as IdP connections are (ADR 063): an identity row, an
immutable revision per write holding the document as authored, and newest by
`created_at`. The other three tables outlive revisions and are written in the
revision's transaction:

| Table | Key | Why |
| --- | --- | --- |
| `apps` | `app_…`, unique slug | Identity and `source` (`declared` or `registered`) |
| `app_revisions` | `apprev_…` | The document; what a release pins |
| `app_clients` | `client_…`, unique `client_id` | The token endpoint finds a client in one lookup, and the id stays with its client |
| `app_api_identifiers` | identifier | `resource` finds its app in one lookup, and an identifier stays with its app |
| `app_client_secrets` | `csec_…` | A registered app's secret hashes |
| `client_registrations` | `dcr_…`, the `client_id` | Clients that registered themselves: their RFC 7591 metadata, a secret hash for a confidential one, and `expires_at`; transient, outside any app |

The document is stored as written, without the minted ids, so a release that
sends the same file again matches its earlier revision. `app.created`,
`app.updated` and `app.client_secret.added` are emitted in the same
transaction ([events catalog](events-catalog.md)); none carries the document
or a secret. A registration emits `client_registration.created`, and a delete
`client_registration.deleted`; a purge emits nothing, as an expiring session
does not.

## API

| Operation | Does |
| --- | --- |
| `POST /apps` | Creates a registered app or revises one by slug; answers each client's `client_id` and the secrets it generated, once |
| `POST /apps/query` | Lists apps at their newest revision, filtered by `slug`, `source` or `created_at` |
| `GET /apps/{id}` | One app with its client ids |
| `GET /apps/{id}/revisions`, `GET /apps/revisions/{revision_id}` | ADR 063's revision reads |
| `POST /apps/{id}/clients/{client}/secrets` | Generates or imports a secret for a registered app's confidential client |
| `POST /client_registrations/query`, `GET /client_registrations/{id}` | Clients that registered themselves, filtered by `created_at` or `expires_at`; never a secret |
| `DELETE /client_registrations/{id}` | Deletes a registration with its consents and their tokens |

Clients register at the authorization server's `POST /register`, which calls
`ClientRegistrationService.Register`; the API has no create for them.

Each app has one writer. `POST /apps` refuses a slug the release declares
(`app.declared`), and a release refuses a slug the API registered: a release
never takes over an app a customer's admin or a product wrote. ADR 081 §12's
adoption of a registered app by a later file waits for team-owned slugs
(`acme/crm`), which make that safe.

## Releases

- **Declared apps are files**, `.zitadel/apps/<slug>.json`, validated against
  `.zitadel/meta/app.json`.
- **The bundle carries them** as `apps[]` in `POST /releases/build`. The build
  validates each as declared, reuses a revision whose document matches,
  appends one when it changed, and pins it under the `app` pointer kind.
  Pointers are JSON, so the kind costs no migration.
- **A deployment serves the revision its release pins.** The authorization
  server reads a declared app at that revision, a registered app at its
  newest, and a built-in app from the binary. Removing a file drops the app
  from the next release, and requests for it fail at the next refresh; the
  stored app and its client ids stay.

## The directory

The authorization server finds clients and APIs through one interface,
[`AppDirectory`](../../../internal/service/app_directory.go):

- `Client(at, client_id)` and `API(at, resource)` return the app at the
  revision that serves `at` (the project and the deployment the request
  resolved, ADR 081 §10).
- `VerifyClientSecret(at, app, client, secret)` checks a registered app's
  hashes or a declared app's frozen variable.
- **Built-in apps** are the third source the POC found: apps the server
  declares, read-only and versioned with the binary, such as the platform
  project's `zitadel`. The directory serves them first.
- **Client ID metadata documents** stay in the authorization server, which
  fetches and caches them; the directory answers not-found for a URL
  `client_id`.
- **Dynamically registered clients** are the directory's too:
  `ClientRegistration(at, client_id)` finds one by its `dcr_…` id,
  `VerifyClientRegistrationSecret` checks a confidential one's secret, and the
  registration's `AccessTo(apiApp, api)` allows a `third_party` API of an app
  that opens dynamic registration.
- **`Registration(at)`** says which registration switches the apps serving
  `at` turn on, a declared app at its pinned revision, so the authorization
  server advertises and opens its endpoints by it.

Part A agreed to this shape: `internal/oauth` replaces its `PlatformApp()`
lookups with these calls, and resolves `AppLookup.DeploymentID` itself
(ADR 081 §10). Also agreed:

- **Without `resource`, a token is for userinfo only** (ADR 082 §5). The
  order of a client's `apis` is the default the SDK sends, not one the server
  applies.
- **A `private_key_jwt` assertion** is checked by the authorization server
  against the client's `jwks`; `VerifyClientSecret` covers secrets only.
- **`scopes_supported` lists exactly what is accepted**, because clients such
  as Claude Code request every advertised scope: an API's protected-resource
  metadata (RFC 9728) lists its own scopes, and the authorization server's
  metadata the built-in ones.
- **Dynamically registered clients are stored**, not sealed into their
  `client_id`, so they can be listed and revoked one by one. A registration
  names no API, so it belongs to the project, not to an app; the app is the
  one whose API a request names, and that app's `registration` must allow it.
  `POST /register` stays the authorization server's endpoint and calls the
  apps write, once `Registration(at)` says an app opens it.
  - **An unused registration expires.** `POST /register` is unauthenticated,
    so a registration has a lifetime of its own (an hour covers the browser
    round trip) and is purged once past it with no live consent naming it.
    A refresh writes nothing to it. The purge rides along with the write
    that grows the table: each registration checks a batch of the project's
    expired ones, deletes those no live consent names, and gives the others
    another lifetime before they are checked again, so they do not hold the
    batch from the rest.
  - **It keeps its own display fields.** With no app document behind it, the
    RFC 7591 `client_name`, `logo_uri`, `client_uri`, `policy_uri` and
    `tos_uri` stay on its record, and the consent step shows them as the
    client's own claims, beside the redirect host, the one part the server
    checked. Control and bidi control characters are refused, so a name reads
    as what it is.
  - **Deleting it deletes its consents and their tokens** in the same
    transaction, as revoking a session deletes its tokens. The authorization
    server implements `ClientRegistrationConsents`: `Named` says which
    registrations a live consent names, for the purge, and `Delete` removes a
    client's consents and tokens, for a delete or a purge. Until it stores
    consents, the server runs with `NoConsents`, and the POC's sealed ids
    keep working beside the store.
  - **A registered client acts for users:** it authenticates with `none` or
    a secret the server generates, uses the code grant with refresh, and
    lists redirect URIs under the same rules as an app client's.

## Lifetimes and claims are policies

Token lifetimes and claim mappings are not fields of the app. They are
policies on token issuance ([ADR 066](../../adrs/066-operation-policies.md)),
because what customers ask for is a hierarchy that no single document holds:

- **Lifetimes per organization first.** The most-upvoted request,
  [#5219](https://github.com/zitadel/zitadel/issues/5219), is per B2B
  tenant, which is a team here; per-client cases (a CLI against a front end,
  [#12653](https://github.com/zitadel/zitadel/issues/12653)) came later.
  Nobody asked for lifetimes per API. Refresh rotation and reuse per client
  ([#9631](https://github.com/zitadel/zitadel/issues/9631)) is the same kind
  of setting.
- **Claims per app or API, with a target and a shape**: roles or groups as a
  flat string array for Grafana, Kubernetes, Argo CD and oauth2-proxy
  ([#9141](https://github.com/zitadel/zitadel/issues/9141),
  [#7042](https://github.com/zitadel/zitadel/discussions/7042)); a claim only
  in one app's tokens ([#8698](https://github.com/zitadel/zitadel/discussions/8698));
  claims only in userinfo to keep cookies small
  ([#12333](https://github.com/zitadel/zitadel/issues/12333)); a scope that
  switches a claim on.

What the policy design has to add, as input to ADR 066:

1. **Templates that return values.** An ADR 066 policy returns allow or deny;
   a lifetime or a claim is a value the token is built with.
2. **An audience** narrower than the project: an app, a client, an API, a
   team. ADR 066 leaves it to the audience model of
   [#1264](https://github.com/zitadel/nextgen/pull/1264).
3. **Who reads a token** is a candidate rule for defaults: an API's settings
   shape its access tokens, a client's its ID tokens, userinfo and refresh
   tokens.
4. **Roles** come from the app: ADR 034's app-group catalog becomes the app's,
   so a token carries the roles of its own app, never another project's
   filtered set.

## SAML IdP configs

Designed, not built. A `saml[]` config makes Zitadel the IdP for a service
provider:

| Field | Holds |
| --- | --- |
| `slug` | As for clients |
| `entity_id` | The SP's entity id, unique per project, as a `client_id` is |
| `acs` | Assertion consumer service URLs with their binding (POST or redirect) |
| `slo` | Single logout URL and binding, optional |
| `metadata_url` | Instead of the three above, the SP's metadata, fetched with ADR 061's egress guards |
| `name_id` | Format (`persistent`, `email`, `unspecified`) and the user property it comes from |
| `attributes` | Attribute name to source, in the claims policy's grammar, so SAML and OIDC map users one way |
| `signing` | Sign the assertion, the response or both; the SP's certificate for signed requests and encrypted assertions |

- **Engine:** in the server beside the OAuth authorization server. Its
  browser endpoints sit under the SDK's `/__nextgen/saml/{project}/…`, which
  the proxy already forwards, so customer apps need no new reserved path. An
  AuthnRequest becomes a flow as an authorization request does
  (ADR 081 §8), which is why it waits for part A's login handoff.
- **Keys:** the project's signing key wrapped in an X.509 certificate
  (ADR 039). `github.com/zitadel/saml` (Apache-2.0, v4's) or
  `crewjam/saml` (BSD-2-Clause) fit [LICENSING.md](../../../LICENSING.md).

## SCIM provisioning configs

Designed, not built. A `scim[]` config makes Zitadel the SCIM client that
keeps the app's own user store in step:

| Field | Holds |
| --- | --- |
| `slug` | As for clients |
| `endpoint` | The app's SCIM base URL, under ADR 061's egress guards |
| `auth` | A bearer token as `${{ NAME }}`, or OAuth client credentials |
| `users` | Which users (by schema or team), the matching key (`externalId` from the user id), and the attribute mapping, property to SCIM path |
| `deprovision` | `deactivate` (`active: false`) or `delete` |
| `groups` | Later: teams as SCIM groups |

- **Engine:** ADR 065 jobs. A user write enqueues a provisioning job in its
  own transaction, and a periodic reconcile pages through the users by
  `updated_at`, so a missed job only delays a push. Audit events are never
  its feed.
- **State:** a row per config and user (remote id, last pushed hash,
  attempts, last error) for idempotency and retries. It is transient: the
  matching key finds the remote user again, so a reconcile rebuilds it.
- It needs nothing from part A, so it is the cheaper of the two to build
  first.

## Console

One Apps screen whose tabs are filters over `POST /apps/query`, in the filter
grammar the CLI shares (ADR 064 §11):

| Tab | Filter |
| --- | --- |
| All apps | none |
| Sign-in clients | a client with `authorization_code` |
| Service accounts | a client with `client_credentials` |
| APIs and MCP servers | an API |
| SAML, SCIM | a config of that kind |
| Open to registration | `registration` on |

The query filters by columns today (`slug`, `source`, `created_at`). The tabs
need facets computed when a revision is written, such as `has_api` and
`has_principal` on `app_revisions`, so every dialect filters them alike.
Clients that registered themselves belong to the project, so they get a
screen of their own over `POST /client_registrations/query`, with a delete;
an app's page can show the ones users consented to for its APIs, from part
A's consents.

## CLI and presets

```sh
zitadel apps create shop --preset web --redirect-uri https://shop.example.com/callback
zitadel apps create orders --preset backend --identifier https://api.shop.example.com
zitadel apps create assistant --preset mcp-server --identifier https://shop.example.com/mcp
zitadel apps create partner --preset web --redirect-uri https://partner.example/cb --registered
```

- **Presets** (`web`, `spa`, `native`, `cli`, `api`, `backend`,
  `service-account`, `mcp-server`) live in
  [`@zitadel/config/app`](../../../packages/config/src/app/presets.ts), so the
  console offers the same ones. A preset only fills the document, and the
  app keeps its name in `preset` as a label, like a connection's `template`.
- **`apps create`** writes `.zitadel/apps/<slug>.json` and names the secret
  variables to set before the deploy that declares the app. `--registered`
  writes the same document through `POST /apps` and shows the client ids and
  the generated secrets once.
- **`apps list`** and **`apps get`** are registry commands. The noun follows
  the CLI's current plural topics and moves to the singular with the
  ADR 064 amendment.
- **`client-registrations list`**, **`get`** and **`delete`** are registry
  commands too: the CLI gives every collection with a query endpoint
  commands (ADR 031). There is no `create`.
- Turning the issuer on in `.zitadel/oauth.json`, as the identity model has
  `app create` do, waits for that file (ADR 082 §12).

## Open questions

1. **Team-owned apps.** Whether an app a product creates for a customer
   belongs to that customer's team, slugged `acme/crm` like a team's
   connection, and whether `team_admin` manages it.
2. **Values per project.** A release ships the same file to staging and
   production, but their redirect URIs and an MCP server's identifier
   differ. `${{ NAME }}` in those fields would resolve per deployment, which
   the identifier lookup table cannot index; a relative form (`/mcp` on the
   issuer's origin) covers the common case.
3. **Deleting an app**, with [#1013](https://github.com/zitadel/nextgen/issues/1013)
   for declared resources.
4. **The secret format** (prefix, checksum) with the apps and machine
   identities note.
