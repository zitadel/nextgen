# External Auth Factors — Research & Design Direction

> **Status:** Research — sharing for feedback, not a final design
> **See also:** [Flow Engine](flow-engine.md) · [Session API](session-api.md) · [Bot Detection](bot-detection.md)
> **POC ADRs:** [015](https://github.com/zitadel/oxidel/blob/main/docs/adr/015-actions-catalog.md) Actions & Catalog, [032](https://github.com/zitadel/oxidel/blob/main/docs/adr/032-backend-layering-use-cases-hooks.md) Use Cases & Hook Pipeline

## Problem

Zitadel natively supports a fixed set of auth factors (password, TOTP, passkey, OTP SMS/email, IdP). Customers regularly ask to integrate factors Zitadel doesn't support natively — Duo, Futurae, custom hardware tokens, internal corporate MFA systems, etc. Building native integrations for every provider is not scalable.

We need a generic extensibility mechanism for external auth factors. This document presents research on how real providers work, identifies the interaction patterns, and outlines design directions. The exact implementation shape is open.

---

## Provider Research

We analyzed five providers that represent the range of what customers ask for. Each has a different protocol, auth scheme, and interaction pattern.

### Duo Security

Duo offers two integration paths:

**Universal Prompt (redirect-based).** OIDC-like, but with Duo-specific deviations. The user is redirected to Duo's hosted UI, authenticates there, and is redirected back.

- Authorize URL: `GET /oauth/v1/authorize` with a `request` param containing a signed JWT (HMAC-SHA512 with the client secret)
- The JWT must include `duo_uname` (the username — Duo requires the user to be identified first)
- Callback returns `duo_code` (not the standard OIDC `code`)
- Token exchange at `POST /oauth/v1/token` returns an `id_token` with `auth_result` and `auth_context` claims
- Health check at `POST /oauth/v1/health_check`
- Credentials: `client_id`, `client_secret`, `api_hostname`

**Auth API (challenge-response).** Server-to-server REST API. No browser redirect. Zitadel calls Duo directly.

- `POST /auth/v2/preauth` — list user's available devices and factors (push, passcode, SMS, phone)
- `POST /auth/v2/auth` — initiate auth. With `async=1`, returns a `txid` immediately. Without, blocks until user responds.
- `GET /auth/v2/auth_status` — poll for async push result (`waiting`, `allow`, `deny`). Supports long-polling.
- `POST /auth/v2/auth` with `factor=passcode` — synchronous code verification
- All requests authenticated with HMAC-SHA1: canonical string signed with secret key, sent via HTTP Basic Auth (`integration_key:hmac_signature`)
- Credentials: `integration_key`, `secret_key`, `api_hostname` (same underlying credentials as Universal Prompt, different names)

### Futurae

Pure API — no hosted UI, no redirect flow. Futurae provides mobile apps and a JavaScript SDK.

- `POST /srv/auth/v1/user/auth` — initiate challenge. Params include `user_id` and `factor` (`approve`, `qr_code`, `totp`, `sms`). Returns `session_id` and optionally `qr_code_url`.
- `GET /srv/auth/v1/user/auth/status` — poll for push/QR approval status (`pending`, `approved`, `denied`, `expired`)
- `POST /srv/auth/v1/user/auth/verify` — verify a code (TOTP, offline, SMS). Params: `user_id`, `factor`, `otp`.
- Auth: HMAC-signed requests or Bearer token, depending on config
- Credentials: `service_id`, `api_key`
- Also has a **JS SDK/widget** that can render QR codes and poll for status client-side

### RSA SecurID

Two integration paths: REST API (modern) and RADIUS (legacy/on-prem).

**REST API (RSA Authentication Manager 8.x+):**

- `POST /mfa/v1_1/authn/initialize` — send username + passcode (PIN + tokencode). Returns `attemptResponseCode`:
  - `SUCCESS` — done
  - `FAIL` — wrong passcode
  - `CHALLENGE` — server needs more info (next-token-mode, new PIN)
  - `ERROR` — system error
- `POST /mfa/v1_1/authn/verify` — respond to a `CHALLENGE` with the next tokencode or new PIN. Same response codes.
- The `CHALLENGE` → `verify` loop can repeat multiple times (multi-step)
- Auth: agent identity (registered in RSA Security Console) + API key or client certificate
- Credentials: RSA AM hostname, agent name, API key or client cert

**RSA SecurID Access (cloud):** Acts as a standard OIDC IdP — supports SAML 2.0 and OIDC redirect. No custom API needed.

### YubiKey OTP

Simplest of all. The YubiKey acts as a USB keyboard — user touches it, it "types" a 44-character OTP string into a text field.

- `GET /wsapi/2.0/verify?otp={otp}&id={client_id}&nonce={nonce}&h={hmac}` — single validation call to YubiCloud
- Response is **key-value pairs** (not JSON): `status=OK`, `t=...`, `otp=...`, etc.
- Response includes an HMAC signature that **must be verified** by the caller
- Status values: `OK`, `BAD_OTP`, `REPLAYED_OTP`, `BAD_SIGNATURE`, etc.
- No challenge initiation — the OTP is generated by the hardware key itself
- Self-hosting possible via `ykval` + `ykksm` (open source)
- Credentials: `client_id` (integer), `secret_key` (Base64), validation URL
- Per-user binding: store the YubiKey's **public ID** (first 12 chars of any OTP from that key)

### RADIUS

Binary UDP protocol (RFC 2865), not HTTP. The "lingua franca" for corporate MFA appliances.

- `Access-Request` → `Access-Accept` / `Access-Reject` / `Access-Challenge`
- `Access-Challenge` enables multi-step flows: server sends `Reply-Message` (human-readable instruction) and `State` (opaque session token). Client must echo `State` back.
- Push-based flows (e.g., Duo via RADIUS proxy): `Access-Challenge` with "Pushed a login request..." message, then poll by re-submitting with the `State` attribute
- Timeout must be 30s+ for push-based MFA (default 5s is too short)
- Auth: shared secret at packet level (used to encrypt `User-Password` and compute the `Authenticator` field)
- **Cannot be proxied through REST** without losing protocol semantics. Needs a native UDP RADIUS client.
- Commonly used by: RSA SecurID, SafeNet/Thales, Duo Authentication Proxy, Symantec VIP, FortiAuthenticator

## Interaction Patterns

The research reveals three distinct patterns for how the frontend, backend, and provider interact:

### Pattern 1: Redirect

User leaves the page, authenticates on the provider's hosted UI, comes back via callback.

```
Frontend → Provider (redirect) → Provider authenticates → Provider → Zitadel callback → Frontend resumes
```

- Backend builds the authorize URL (may involve JWT signing, nonces, etc.)
- Frontend just navigates to the URL and waits for the callback
- Backend verifies the result on callback (code exchange, token verification)
- **Backend holds credentials**: always (client_id, client_secret, signing keys)

| Provider | Notes |
|---|---|
| Duo Universal Prompt | OIDC-like but with extensions (JWT request, `duo_code`) |
| RSA SecurID Access (cloud) | Standard OIDC |

### Pattern 2: Server-Side Challenge-Response

Backend calls the provider API to initiate a challenge, gets back data, builds the UI for the frontend. Frontend renders it and submits user input. Backend verifies with the provider.

```
Backend → Provider (initiate) → Backend builds BDUI → Frontend renders → Frontend submits → Backend → Provider (verify)
```

- Backend initiates the challenge and controls the entire conversation
- Frontend receives standard BDUI fields and doesn't know about the provider
- Some providers need multiple rounds (RSA `CHALLENGE`, RADIUS `Access-Challenge`)
- Some providers need a preauth step (Duo lists devices before auth)
- Poll-based flows (push notifications) need async status tracking

| Provider | Auth scheme | Multi-step? | Poll? |
|---|---|---|---|
| Duo Auth API | HMAC-SHA1 signed requests | No (but has preauth) | Yes (push) |
| Futurae | HMAC or Bearer | No | Yes (push, QR) |
| RSA SecurID (REST) | Client cert | Yes (next-token, new PIN) | No |
| YubiKey OTP | HMAC-SHA1 | No | No |
| RADIUS | Shared secret (UDP) | Yes (Access-Challenge) | No |

### Pattern 3: Client-Side Widget

Provider offers a JavaScript SDK that runs in the browser. The widget communicates directly with the provider, handles the UX, and produces a signed token. The backend only needs to verify the token.

```
Frontend loads provider JS SDK → Widget ↔ Provider (direct) → Widget produces signed token → Frontend submits token → Backend verifies token
```

- Backend makes one verification call instead of managing the full challenge lifecycle
- Frontend loads provider-specific JavaScript (not pure BDUI)
- Lower latency (frontend talks to provider directly)
- Requires the provider to offer a JS SDK

| Provider | SDK | Notes |
|---|---|---|
| Duo Web SDK (older iframe-based) | `Duo-Web-v2.js` | Renders Duo iframe, produces `sig_response` |
| Futurae | Futurae JS SDK | Renders QR, handles polling |
| Captcha providers (reCAPTCHA, hCaptcha, Turnstile) | Provider JS | Same pattern — widget produces a token |

This pattern is essentially **how captcha already works** in the flow engine: the frontend runs the provider's script, gets a proof token, and submits it for backend verification.

## Key Design Constraints

The research surfaced several constraints that any implementation must address:

### 1. Credentials always live on the backend

Every provider requires server-side secrets for at least the verification step. Even widget-based flows need backend verification — a malicious frontend could fabricate a "verified" response. The backend must always be the authority that records the factor on the session.

### 2. No single auth scheme covers all REST providers

| Provider | Auth scheme |
|---|---|
| Duo Auth API | HMAC-SHA1 request signing (canonical string) |
| Futurae | HMAC-signed or Bearer token |
| RSA SecurID | Client certificate (mTLS) |
| YubiKey OTP | HMAC-SHA1 on both request and response |

A generic REST integration must support multiple authentication methods.

### 3. RADIUS is not REST

RADIUS is a binary UDP protocol with packet-level authentication. It cannot be meaningfully proxied through a generic REST adapter. If we want to support the large installed base of RADIUS-based corporate MFA, we need native RADIUS support. Go has libraries for this (`layeh.com/radius`).

### 4. Multi-step challenges are real

RSA SecurID's "next-token-mode" and RADIUS's `Access-Challenge` mean a single request-response isn't always enough. The system must support re-rendering the same step with updated content until the provider returns accept or deny.

### 5. Duo's OIDC is not standard OIDC

Duo Universal Prompt requires a signed JWT request object with a `duo_uname` field, uses HMAC-SHA512 instead of RS256, and returns `duo_code` instead of `code`. A pure standard OIDC adapter won't work without extension points.

### 6. Not all providers have an initiate step

YubiKey OTP has no challenge initiation — the user just touches the key. The OTP goes straight to verification. The design must handle verify-only flows.

### 7. Response formats vary

Most REST APIs return JSON, but YubiKey OTP returns key-value pairs, and RADIUS returns binary AVPs. The system needs to handle different response formats.

## Design Directions

Based on the research, here are the directions we're considering. The exact shape is not decided.

### What's clear

- **Two step types** in flow definitions: `external_redirect` (user leaves the page) and `external_challenge` (in-page interaction). The frontend contract is different enough to justify separate types.

- **A new resource type** for provider configuration: `external_factor_provider` (separate from IdP providers). It holds credentials, connection details, and factor properties (ACR contribution, hardware/phishing-resistant flags).

- **A separate callback endpoint** for external factor redirects (`/external-factor-providers/{id}/callback`), distinct from `/idp/callback`. The external factor callback only verifies the MFA result and records a factor — no user provisioning, no claim mapping.

- **Factor properties** on the provider resource determine how the factor participates in ACR evaluation, regardless of protocol:
  ```json
  {
    "contributes_to_acr": true,
    "acr_methods": ["mfa", "otp"],
    "hardware": false,
    "phishing_resistant": false
  }
  ```

- **Challenge context is opaque to the frontend.** The frontend holds an encrypted blob and sends it back on submit. All verification logic is server-side.

### What's open

**How to structure the protocol layer.** Options include:

- **Protocol adapters built into the engine** — a small set (OIDC, REST, RADIUS) with protocol-specific config. Covers all researched providers. Extensible by adding new adapters. Risk: the REST adapter config surface may become complex to cover all auth schemes and endpoint patterns.

- **Plugin/scripting approach** — provider integration logic as scripts (e.g., expr, Rego, Lua). Maximum flexibility, but harder to secure and debug. The config becomes a mini-program.

- **Start narrow, expand later** — ship with OIDC redirect support only (covers Duo Universal Prompt, RSA cloud), then add REST and RADIUS in later iterations based on demand.

**Whether to support client-side widgets.** The widget pattern (provider JS SDK running in the browser) has real benefits — lower latency, simpler backend, the provider handles its own UX. But it means loading third-party JavaScript and breaking the pure BDUI model. Options:

- **BDUI field type `widget`** — the step response includes a script URL and config. The frontend loads it and renders the widget in a container. The widget produces a token that gets submitted. This is already how captcha works.

- **Keep it server-side only** — simpler, more secure (no third-party JS), consistent BDUI. Accept the extra backend round-trips.

- **Both** — default to server-side, allow widget mode as an opt-in for providers that offer it.

**How the REST adapter describes the challenge UI.** When the backend initiates a challenge, it needs to know what BDUI fields to render. Options:

- **`challenge_ui` template on the provider resource** — the admin defines fields/actions as BDUI templates with `{placeholders}`. The engine fills in values from the provider's response. Generic but adds config complexity.

- **Convention-based** — the engine infers the UI from the provider's response and a small set of hints (e.g., `"ui_mode": "push_with_code_fallback"`). Simpler config but less flexible.

- **Step-level override** — the flow definition's step config can override the provider's default UI. Allows the same provider to render differently in different flows.

**How to handle user-to-provider binding.** Providers need to know which user is authenticating. Some use the login name, others require a provider-specific user ID (e.g., Futurae `user_id`). This raises questions:

- Where is the mapping stored? On the user resource? On the provider resource?
- How is enrollment handled? Some providers (Futurae, RSA) require explicit user enrollment before authentication is possible.
- Is enrollment a flow step, an admin action, or a self-service action?

**RADIUS priority.** RADIUS support requires a native UDP client and adds operational complexity (network access, shared secret management). It's primarily needed for on-premise deployments with legacy MFA infrastructure. The question is whether to include it from the start or defer it.

## Boundary with Other Systems

The flow engine's only extensibility points are `external_redirect` and `external_challenge` steps. Everything else belongs elsewhere:

| Capability | Owner | Why not the flow engine? |
|---|---|---|
| Block submission based on input | **Policy engine** (TBD) | Blocking is a policy decision |
| Validate fields (regex, webhook) | **Policy engine** (TBD) | Validation rules are policy |
| Inject captcha, step-up based on risk | **Policy engine** (TBD) | Risk evaluation is policy |
| Decide which transition to follow | **Policy engine** via `policy_check` | Already works this way |
| Webhooks, notifications | **Domain event handlers** (ADR-032) | Triggered by business events (`UserCreated`, `SessionStarted`), not step transitions |

**Why webhooks don't belong on flow steps:** "Notify Slack after the profile step" is really "notify Slack when a user is created." The right trigger is the `UserCreated` domain event, not a step transition. Domain events are durable, retriable, and work regardless of whether the user came through the flow engine or the Session API.
