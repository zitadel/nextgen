# Identity Providers

This document contains planning notes for
[zitadel/nextgen#851](https://github.com/zitadel/nextgen/issues/851) - "Enable
social login with Google and GitHub": letting developers enable social sign-in
from the CLI and guiding them through the provider setup it requires.

**Status:** Technical design discussion.
There is no IdP server contract yet.

On a high level,
- Provider connections are separate Project-level resources and may be shared by several user schemas
- As authentication methods belong to a user schema, the user schema lists which connections its users may sign in with (`x-auth-methods.sso.providers`)
- A flow step then offers the provider connections referenced by the user schema
- The provider connections are configured in the CLI (configuring in Console is out-of-scope)

## Product decisions

| Decision                                      | Status in the docs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Options                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Where                                                                                              |
|-----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| One connection shared by several user schemas | A user belongs to one schema, and an identity link is `(connection, subject)` with no reference to the user schema. When the same user arrives through a different schema (e.g., Customer and Employee user schemas), the request is failed with a flow-level error.                                                                                                                                                                                                                                                                                                                            | • resolve to the same Project user<br>• allow a separate user under each schema: the link becomes `(connection, schema, subject)`. Needs a schema identity that survives a republish, since `users.schema_url` names one revision rather than the schema, and a per-schema uniqueness scope (`x-unique` offers project or team), or the second sign-up collides on shared unique properties and reaches the conflict step<br>• refuse the identity for the second schema | [3](3-social-login-flow.md#open-points), [1](1-resource-model.md#linking-safety)                   |
| Provisioning on the connection or in a policy | The connection carries `creation` as a ceiling. Per-user-type behaviour (Customers may sign up with Google, Employees only sign in) belongs to authentication method settings ([#898](https://github.com/zitadel/nextgen/issues/898)), #898 states that the effective rule is the intersection, so the policy can narrow the connection's value and never widen it. 851 includes the connection layer only.                                                                                                                                                                                     | • ceiling on the connection, narrowed by a later policy<br>• policy only: #898 has no resource yet, so 851 would have no creation control<br>• a per-connection policy file (`.zitadel/policies/idps.json` with a per-slug list): #898 keys social settings by method kind, not by provider                                                                                                                                                                              | [1](1-resource-model.md#provisioning)                                                              |
| Edits that change who a subject is            | Identity links key on the connection id. An in-place change of `subject_claim` or of the authority (`issuer` for OIDC, the token and userinfo endpoints for OAuth2) would re-key every link: subject `12345` at Company B's tenant resolves to the account Company A's `12345` created. The docs fix these fields for the life of a connection, similar to the slug; the CLI refuses the edit and the server refuses the revision. OIDC endpoint overrides stay editable, since the `issuer` pins the authority. A real authority change is a new connection, and users sign up again under it. | • fixed for the connection's life<br>• warn and re-key (the earlier text; allows a custom-domain move in place at the cost of the reassignment above)<br>• a link-transfer operation for legitimate migrations: not designed, returns with custom providers, whose issuers can move                                                                                                                                                                                      | [1](1-resource-model.md#connection-lifecycle)                                                      |
| What `enabled: false` means for a method      | A provider is in one of four states for a user type ([provider states](2-auth-method-selection.md#provider-states)):<br>• connection defined, but unused<br>• listed in a user schema, but not enabled in flows<br>• enabled in flows<br>• removed<br>A disabled slot is always `{"enabled": false}` with no `providers` array; a flow that still offers the provider is a validation error, as it is for `password` today.                                                                                                                                                                     | • disabled means removed: a flow that still offers the provider fails validation before apply, the validator says which step to fix, and the CLI picker makes the schema and flow edits (designed)<br>• disabled pauses: flows keep their steps, the engine hides the buttons at render. Rejected: an SSO-only step would reach the engine with zero user inputs, a state the engine cannot currently handle ([area 2](2-auth-method-selection.md#provider-states))      | [2](2-auth-method-selection.md#provider-states)                                                    |
| Removing a method existing users depend on    | This issue is not specific to SSO. Removing an authentication method (such as passwords) risks permanently locking out users who rely exclusively on it. Once a method is removed, the flow only offers the remaining options, creating a deadlock: adding a new credential to an account requires authenticating first, a proof the user can no longer provide (this exact deadlock also occurs when transitioning a schema from passwords to passkeys). Email recovery isn't available yet.                                                                                                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | [2](2-auth-method-selection.md#provider-states)                                                    |
| Social sign-in in pattern environments        | Providers accept only registered, exact redirect URIs, and an `issuer_pattern` environment (per-PR previews) has a new origin for every deployment. The plan is to hide the provider buttons at render in such environments, record a diagnostic, and let the release deploy; the plan returns a warning. Social sign-in is tested in development and on exact environments.                                                                                                                                                                                                                    | • hidden at render, release promotes unchanged<br>• error during deployment: a project with previews could never promote a release containing social login<br>• serving dynamic origins at all: open, platform-level ([#534](https://github.com/zitadel/nextgen/issues/534)); any approach needs a fixed registered callback that hands back to the originating origin, and area 3 records the constraints such a design must meet                                       | [3](3-social-login-flow.md#open-points), [4](4-cli-provider-setup.md#multi-environment-evaluation) |
| Superset or 1:1 for schema-keyed fields       | As the same Project-level provider connection can support multiple user schemas, one connection's `claim_mapping` and `verified_claims` may name properties of several schemas. How strictly can these fields be checked during validation? A typo and a key meant for another schema are indistinguishable by the validator.                                                                                                                                                                                                                                                                   | • superset: one connection reused across schemas, partial mismatches return warnings<br>• 1:1: one connection per schema even for the same OAuth app; error-grade checks, identity resolution would be schema-specific by construction, and connection config and credentials would be duplicated                                                                                                                                                                        | [1](1-resource-model.md#open-points)                                                               |
