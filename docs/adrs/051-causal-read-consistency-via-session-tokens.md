# ADR 051: Causal Read-Consistency via Session Tokens for PostgreSQL and Spanner Replicas

- Status: Proposed
- Date: 2026-08-12

## Context

We plan to add read replicas — PostgreSQL streaming replicas and Cloud
Spanner read-only replicas — for read scaling. Both dialects are already
first-class peers in the storage layer (ADR 028: `internal/storage/dialect/postgres`
and `internal/storage/dialect/spanner`, both behind one `Pool` interface in
`internal/storage/database/pool.go`), but that `Pool` is single-target today
— there is no read/write split and no replica routing anywhere in the
codebase. Introducing replicas without a consistency mechanism would let a
caller write through the primary and then read stale data from a lagging
replica on their very next request, breaking **read-your-writes** (session
causal consistency), which is the one guarantee the API must never drop
even while scaling reads.

The ask that motivated this ADR was to round-trip an opaque database
consistency watermark — a PostgreSQL LSN or a Spanner commit timestamp —
through the existing Session Token, so writes stamp the watermark and reads
present it back to force a replica to catch up (or fall back to primary).
This ADR records why we are *not* doing that literally, and what we do
instead.

## Audit of existing ADRs (Step 1)

No ADR in `docs/adrs/` addresses read replicas, replication lag, LSNs, or
causal consistency before this one. The closest prior art:

- **ADR 037 — Token Lifecycle** (Accepted): the session token is an opaque,
  server-authoritative JWE. Its validity is re-checked against a DB row
  (the `tokens` table) on every use — revocation is immediate because the
  row, not the token payload, is authoritative. The session token's stated
  design goal is to be *minimal*: "the stored representation should be
  minimal: only the token ID." Anything we add must not fight that
  minimality goal or the DB-row-is-authoritative model.
- **ADR 036 — API Credential Planes** (amended 2026-08-03): the session
  token rides the `__nextgen_session` HttpOnly cookie and is explicitly
  never script-readable. Any new value that travels alongside session
  identity inherits this exposure contract unless we deliberately decide
  otherwise.
- **ADR 028 — Storage v2: Typed Statements and Per-Dialect SQL** (Proposed,
  partially implemented): establishes the per-dialect statement pattern and
  the single, non-replica-aware `Pool`. This is where dialect-owned
  consistency primitives belong, mirroring how ADR 047 put ID generation
  behind dialect-owned logic rather than a shared helper.
- **ADR 047 — Dialect-Owned Identifier Generation** (Accepted): precedent
  for encoding a backend-specific concept (there: PK generation; here:
  commit watermark) behind one portable interface implemented differently
  per dialect.

## Audit of the session token (Step 2)

`internal/domain/token.go` defines:

```go
type Token struct {
    ProjectID string
    TokenID   string
    UserID    string
    Type      TokenType
    SessionID     *string
    OIDCSessionID *string
    SAMLSessionID *string
    Scope         []string
    CreatedAt     time.Time
    ExpiresAt     *time.Time
}
```

This struct is JSON-marshaled and encrypted into a JWE
(`(t *Token) JWE(encrypter)`); the session token is minted once per session
(`internal/domain/session.go: (s *Session) Token(...)`) and reused for the
life of the session. There is no version field and no enforced size limit —
the JWE grows with whatever is JSON-marshaled into `Token` — so *mechanically*
a new field could be added. But two things make embedding a
write-driven watermark here the wrong choice:

1. **Lifetime mismatch.** The token is minted once and then only
   re-validated (decrypt + DB lookup), never re-minted, until the session
   ends or is exchanged. A causal-consistency watermark changes on every
   write. Keeping it fresh inside the token would mean re-encrypting and
   re-issuing a new `Set-Cookie` on every write request — a much bigger
   behavioral change to a security-sensitive, revocable credential than the
   read-consistency problem requires.
2. **The DB row is already the authoritative, cheap place to put mutable
   per-session state.** `IntrospectToken` already looks up `TokenID` in the
   `tokens` table on every validated request (`internal/storage/dialect/postgres/token.go`,
   mirrored in `.../spanner/token.go`). A per-session watermark column on
   that existing row (or on the `sessions` row it points at) is updated by
   write statements and read back on the same lookup that already happens —
   no JWE growth, no re-mint, no new `Set-Cookie` cadence change.

## Audit of endpoint transport (Step 3)

The API is pure HTTP/REST generated by ogen from `api/openapi/**` — there is
no gRPC service in this repository. Session-cookie handling is **opt-in per
OpenAPI operation** via the `nextgenSession` security scheme
(`internal/api/security.go: SecurityHandler.HandleNextgenSession`), declared
today on only three operation groups: `sessions/me`, `users/me`, and
`projects/{id}/claim/complete`. Generic middleware
(`internal/api/middleware/*`, chained in `cmd/server/server.go`) runs on
every request (request ID, logging, `X-Forwarded-*`) but does not touch the
session cookie — that only happens inside per-operation generated dispatch.

This means: **most read and write endpoints never look at the session token
at all today.** If a consistency watermark were coupled to the
`nextgenSession` security scheme, it would only ever reach the 3 endpoint
groups that declare it — defeating the purpose, since read-your-writes needs
to hold across the whole read/write surface (public, app, and operator
credential planes per ADR 036), not just the session-scoped `/me` endpoints.

A repo-wide search for `ConsistencyToken`, `CausalToken`, `ReadYourWrites`,
`LSN`, `CommitTimestamp`, `WaitLSN`, "read replica," and "sticky routing"
found no existing machinery of this kind. Spanner reads currently go through
`client.Single()` (strong reads by default), so the absence of a
consistency mechanism has not mattered yet — it will as soon as any replica
is introduced.

## Decision

1. **Do not carry the watermark inside the encrypted session-token JWE.**
   The session token stays exactly as defined in ADR 037. Read-consistency
   is a separate concern, only incidentally related to session identity.
2. **Transport the watermark as its own small, opaque value, applied via a
   generic (non-opt-in) code path** — not gated by the `nextgenSession`
   security scheme — so it can accompany any read or write request
   regardless of credential plane. The exact carrier (a dedicated header
   such as `X-Zitadel-Consistency`, an `ETag`-style value, or a companion
   cookie scoped to the same session) is left as an **open point for
   implementation-time decision**, not resolved here, because:
   - A header is the most general (works for all three ADR 036 credential
     planes, not just cookie-authenticated `/me` calls) and needs no new
     cookie-exposure rule under ADR 036.
   - An `ETag`-style value borrows familiar HTTP semantics but `ETag` is
     conventionally resource-scoped/caching-scoped, not session-scoped —
     reusing it here risks confusing two different mechanisms.
   - A companion cookie stays closest to "attached to the session" but adds
     a second cookie to every request and still needs an ADR 036 exposure
     classification.
   Whichever is chosen, it must be opaque to the client and dialect-tagged
   internally (e.g. `pg:<lsn>` / `spanner:<rfc3339nano>`), never a bare LSN
   or timestamp the client could interpret or forge.
3. **Encoding per dialect:**
   - **PostgreSQL**: write path captures `pg_current_wal_lsn()` in the same
     transaction as the write; read path waits for the target replica to
     reach that LSN. Native `pg_wait_lsn` requires PostgreSQL 17+ — until
     the minimum supported Postgres version guarantees that, use bounded
     polling (`pg_last_wal_replay_lsn()` on the replica) as the wait
     primitive, revisited when the version floor moves.
   - **Spanner**: write path captures the `CommitTimestamp` returned by the
     commit response of `ReadWriteTransaction`/`Apply`; read path uses a
     stale read with `ExactStaleness`/`ReadTimestamp` bounded to at least
     that commit timestamp — Spanner supports this natively, no polling
     needed.
4. **Fallback strategy**: bound the wait for replica catch-up with a short
   timeout; on timeout, route the read to the primary rather than serving a
   possibly-stale result. Never silently serve stale data past the
   deadline — fail toward strong consistency, not toward staleness.
5. **Storage-layer prerequisite** (explicitly out of scope for this ADR,
   flagged as a dependency): the `Pool` interface (ADR 028) has no notion of
   a secondary/replica target today. A replica-aware `Pool` (or a sibling
   interface for routing reads) must exist before the wait/fallback
   primitives above have anywhere to route to. This ADR defines the
   consistency-token contract; a follow-up ADR or an amendment to ADR 028
   should define replica-aware pooling itself.

## Rejected alternatives

- **Embed the watermark in the session-token JWE.** Rejected: lifetime
  mismatch (per-write mutation vs. mint-once token), and narrow transport
  coverage (only 3 of many endpoint groups validate the session token
  today). See "Audit of the session token" and "Audit of endpoint
  transport" above.
- **Always read from primary.** Rejected: defeats the purpose of adding read
  replicas in the first place; kept only as the fallback-on-timeout
  behavior in item 4, not as the default.

## Consequences

- Session tokens (ADR 037) are unaffected — no schema change, no re-mint
  cadence change.
- A new small piece of per-session mutable state is introduced (the
  watermark), living on the existing `tokens`/`sessions` DB row rather than
  in the encrypted token payload.
- A new generic request/response path must exist so the watermark can
  travel independent of the `nextgenSession` security scheme; this touches
  the shared middleware chain (`internal/api/middleware`), not per-operation
  security handlers.
- Any read replica introduced before the wait/fallback primitives and a
  replica-aware `Pool` exist would violate read-your-writes; this ADR's
  primitives are a hard prerequisite for turning on replicas, not an
  optional hardening step.
- The exact wire carrier for the watermark (header vs. `ETag`-style vs.
  companion cookie) remains an open implementation decision, to be settled
  when this ADR moves from Proposed toward Accepted.

## Amends / amended by

- Notes ADR 037 (Token Lifecycle) is unaffected by this decision; the
  session token's structure and validation are unchanged.
- Notes ADR 036 (API Credential Planes) will need an exposure-contract
  entry for whichever transport carrier is chosen in a future revision of
  this ADR.
- Depends on a future amendment to ADR 028 (Storage v2) for replica-aware
  `Pool` routing, without which the fallback strategy in this ADR has no
  primary to route to.
