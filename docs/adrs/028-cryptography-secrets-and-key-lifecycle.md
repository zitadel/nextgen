# ADR 027: Cryptography, secrets and key lifecycle

> **Status:** Proposed
> **Date:** 2026-06-24
> **Context:** cryptography, secrets and key lifecycle

## Context

Currently, there is not a unified architecture for generation, storage,
rotation, and publication of cryptographic materials. This ADR will define:
project/preview secret handling, KMS/envelope encryption boundaries, signing key
(JWKS) lifecycle and rotation, password hashing policy and rehash/migration
strategy, and crypto-agility/FIPS constraints. Without this, key rotation
mistakes, secret sprawl, and inconsistent hashing will threaten production
security and availability.

## Decision

### Password/secret hashing

For password hashing we use the [`passwap`](https://github.com/zitadel/passwap) 
package. It provides all functionality to hash and migrate hashes of passwords.

A project admin should be able to configure which hashing method should be used.
This so that a tenant can have specific requirements like FIPS.

By default, we should use `argon2id` for password/secret hashing.

### Project/preview secret

With the "claim later" project creation model, a project should generate a 
secret with which a customer can set up/view/modify their project. This secret 
will be an encrypted JWT with the project id and scopes as claims.

Project secret:
```json
{
  "jti": "tkn_123",
  "projectID": "abcd1234",
  "scope": "project.write project.read",
  "iat": 1782453167,
  "exp": 1782705247
}
```

Preview secret:
```json
{
  "jti": "tkn_124",
  "projectID": "abcd1234",
  "scope": "project.read",
  "iat": 1782453167,
  "exp": 1782705247
}
```

Each token should have an expiration time which can be configured at server
level. The expiration time of the project secret should be in line with the 
time a project can exist without claiming.

Each token should have a token id (`jti`). This can be used to revoke a token
in case of a leak.

### Signing keys

The application will use a single master-key. This key is used for encrypting
sensitive information, like OIDC signing keys, in the database. This master-key 
should be provided as an asymmetric key pair. That way, the key can be rotated 
just like any other secret.

The signing keys, like OIDC JWKS, should be generated by the server. The 
maximum age of all generated keys should be configurable.

An application flag should be available to generate a master key if none is
provided or available. This key should then be saved to disk for later use. 
This to make testing the product easier.
