# ADR 042: Dialect-Owned Identifier Generation

> **Status:** Accepted
> **Date:** 2026-07-30
> **Context:** Completing storage-owned ID generation (ADR 028 §8)
> **Amends:** [ADR 011](011-resource-identifiers.md) package roles and managed create semantics;
> completes the open checklist item in [ADR 028](028-storage-v2-statements-and-dialects.md)

## Context

nextgen persists two identifier classes ([ADR 011](011-resource-identifiers.md)):

1. **Ephemeral** — DB-generated integers for short-lived auth lifecycle rows.
2. **Managed** — prefixed API strings for durable resources (users, teams, projects, …).

ADR 028 §8 moved ownership of generation into v2 dialects, but call sites still
minted managed IDs in `internal/domain/idgen` and some service/flow code. HTTP
create bodies sometimes allowed clients to smuggle a resource primary key
(notably via `additionalProperties` on the user schema). Generation belonged
next to dialect DDL and insert semantics so each engine can choose the mechanism
that fits it.

## Decision

### 1. Dialects own all resource ID generation

| Class | PostgreSQL | Spanner | Why |
|---|---|---|---|
| **Ephemeral** | `BIGINT GENERATED ALWAYS AS IDENTITY` (monotonic); read back via `RETURNING` | `INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE)`; read back via `THEN RETURN` | Postgres accepts monotonic keys (often with hash partitioning). Spanner bit-reverses to avoid hotspots. Integer alignment keeps one Go `database.Identity` scan path. |
| **Managed** | Prefixed ULID in Go (`prefix_<ulid>`) at create when the ID is empty | Same prefixed ULID in Go | Branded, time-sortable strings; required prefixes keep `Identity.Value` from treating them as integers. Both dialects share the algorithm today; either may later switch to a DB function without changing domain. |

Shared ULID code lives under
[`internal/storage/v2/dialect/idgen`](../../internal/storage/v2/dialect/idgen/)
as a dialect-layer helper — not under `internal/domain`.

Domain keeps **prefix constants** and validation only. Domain and service
constructors leave managed IDs empty; create/upsert statements fill them in
via `idgen.Ensure` (assign when empty; keep non-empty for ceremony ids,
schema `$id` URIs, and bootstrap/test fixtures). Client-supplied resource
PKs are rejected at the HTTP edge (create-user handler), not in `Ensure`.

### 2. HTTP create never accepts resource primary keys

Create request bodies must not accept a client-chosen resource PK. The server
always assigns managed IDs (via the dialect) and ephemeral IDs (via DB
identity). Responses expose the assigned `id`.

OpenAPI documents the forbid (`not: { required: [id] }` on the user create
schema). ogen does not enforce that keyword, so the create-user handler
rejects a client-supplied `id` with 400.

### 3. Exceptions (not resource PK generation)

| Case | Rule |
|---|---|
| JSON Schema `$id` | Client-authored document URI (GitOps-stable). If omitted, dialect generates `sch_<ulid>` on create. |
| SSO provider `id` in flow definitions | Config key inside the definition document, not a storage PK. |
| Middleware `req_*` | Request correlation IDs; may use dialect `idgen` but are not persisted resource PKs. |
| Secret tokens (`sk_*`, handoff tokens) | Cryptographic secrets, not resource identifiers. |

### 4. Pre-persist ceremony IDs

Flows that need a managed ID before the insert (e.g. provisional `user_*` for
passkey registration, `pkreg_*`, in-memory `flow_*` handles) obtain IDs from a
**dialect-owned** `NewManagedID` on the storage pool/statements — never from
domain-layer minting or from the HTTP client. Passkey registration mints the
provisional `user_*` inside `PasskeyRegistrationService.Begin` when the caller
has no user id yet.

## Consequences

### Positive

- One ownership story: dialects decide how IDs are produced; domain validates shape.
- Clients cannot collide or forge resource PKs on create.
- Ephemeral generation stays engine-native (ADR 011 DDL unchanged).

### Negative / Risks

- Passkey and flow wiring must inject the dialect generator instead of
  constructing `domain/idgen` directly.
- Schema `$id` remains client-controllable by design; uniqueness is still
  enforced at insert.

## Follow-ups

None required to close ADR 028’s ID-generation checklist item. Future dialect
divergence (e.g. Postgres SQL function for managed IDs) can amend this ADR’s
mechanism table without changing the ownership rule.
