"@zitadel/cli": minor
"@zitadel/config": minor
---

`zitadel plan` and `zitadel apply` now check the SSO configuration across files before anything is sent, and stop with one error that names the file, the steps and the name at fault, and what to change. It reports what the plan touches and the files those reference, so an older mistake in an unrelated file does not stop an edit. It catches a step that offers a provider its user schema does not list, or when SSO is off; a schema that lists a provider with no connection file; a step that offers providers but does not route every outcome (a `user_already_exists` route that carries an action does not count); a claim mapping that fills nothing the schema defines; a mapping or `verified_claims` key that names a property no schema has (a top-level name, not a dotted path); and a `verified_claims` key with no `claim_mapping` row. A connection that cannot create users needs only `sso_authenticated` routed and no claim mapping. `@zitadel/config/validate` is now one validation library: `validateFlowDefinition` for a single flow and its schema, and the new `validateProject` for the whole working tree, with every rule named once in a typed registry. `FlowValidationRuleId` is now `FlowRuleId`; the old name stays as a deprecated alias.

Connection files are held to the platform too, and none of these checks is turned off by `ZITADEL_SKIP_FLOW_VALIDATION`. Two files with the same slug or the same project variable stop `plan` and `apply`. A `client_id` or `client_secret` that names a project variable must find it: a missing one fails with `E_CREDENTIAL_MISSING`, a client secret that is not a secret variable, a client id that is a secret one, or one variable for both is refused. Editing the `slug`, `protocol`, `oidc.issuer`, the OAuth2 endpoints or `subject_claim` of a connection that was already applied (an absent OIDC `subject_claim` reads as `sub`) is refused with the field and file named. `plan` stops when the project's variables or an edited connection's stored copy cannot be read, instead of skipping the checks.

A removed connection file is reported apart from the changes, because the platform cannot delete it yet: `plan --json` and `apply --json` carry `unsupported_deletions` (a count, with the files in `unsupported_deletion_files` on `apply`), the headline no longer says "no changes", and `apply` no longer says everything is in sync. A renamed connection file is planned and reported as a move (`move` in `changes`, with `moved_from`), shown as a diff against the stored connection.
