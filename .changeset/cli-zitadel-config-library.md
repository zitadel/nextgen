---
"@zitadel/cli": minor
"@zitadel/config": minor
---

Every command now reads, checks and writes `.zitadel/` through one configuration library, so they all hold the files to the same rules and refuse with the same errors. `@zitadel/config` adds `referencedClientIdVariable` and `referencedClientSecretVariable`, which read a credential reference as the variable it names.

**Breaking:** `deploy`, `preview` and `release create` refuse an invalid configuration with one `E_VALIDATION`, "Configuration validation failed (N issues)", whose `details.issues` lists `{rule, path, steps?, message}`; the separate "Flow validation failed", "SSO configuration is not consistent" and "Missing environment variables" errors and the `handle` and `step` fields are gone, a missing variable is an `environment/missing-variable` issue for each file that references it, and warnings name the file. `setup` writes the configuration and publishes it in its first deploy instead of creating each resource on its own. When that deploy is refused, `setup` still succeeds, keeps the project and files, and suggests `deploy`. The `auth-method` commands refuse when any file under `.zitadel/` does not parse, fails its contract or fails the per-file checks `deploy` makes (a literal `client_secret`, a branding template or `$file` that cannot be read, an unknown connection field, endpoint problems), even a file the command does not change, and refuse to write or remove a file whose path resolves outside `.zitadel/`, through a symlink for one. `auth-method` results report `notices` instead of `kept` and `untouched`. New `.zitadel/state.json` files have no `resources` section, so an older CLI fails on them. `setup`, `branding eject` and `doctor --fix` never replace a `.zitadel/meta/` schema when the project pins a newer `@zitadel/*` package. `doctor`'s schema check validates every file under `.zitadel/`. `auth-method sso enable` now keeps a provider route it did not write and says so, instead of resetting it. `deploy` no longer only warns when a release would leave existing users unable to sign in: it asks first, and a non-interactive run, `deploy --dry-run` included, refuses with `E_CONFIRMATION_REQUIRED` unless it is given the new `--force`. A lockout check that could not finish still only warns. Deploy's lockout check no longer follows a transition into another flow, and a literal `client_secret` is refused by the `connection/literal-secret` rule. `deploy` also refuses a schema or flow step that lists the same provider twice (`sso/duplicate-provider`), a connection with a field its contract does not know (`sso/unknown-connection-field`), a claim name with surrounding whitespace (`sso/claim-name-whitespace`) and a sign-up through a connection that can create a user without an attribute the schema requires (`sso/collection-misses-required`). It warns about a claim whose scope the connection does not request (`sso/claim-needs-scope`), a claim mapped to a property of another type (`sso/claim-type-mismatch`), a verification source that is not a boolean claim (`sso/verification-source-not-boolean`) and a subject claim that can change (`sso/subject-claim-unstable`).

`doctor`'s schema check may list the project's connections on the server, using `zitadel.json` and `.zitadel/secret`, when `sso/subject-claim-unstable` could apply; it and `deploy` leave that warning out when the listing cannot be read, and `doctor` checks no environment, so `environment/missing-variable` is `deploy`'s alone. A flow is matched to a local schema by `objectType`, `$id`, the id in `.zitadel/state.json` or the file name at the end of its `user_schema` URL, so flow and SSO rules can apply where they did not. `pull` refuses before it writes anything for an unsafe handle, two broken files holding one handle or two pinned handles resolving to one file. `auth-method sso enable` reports the claim-mapping summary as an `info` notice in `--json`. `setup --dev-port` lists providers by connection slug and stops when `.zitadel/idps` cannot be read, and `policies test` reports an invalid policy file in `details.issues`. A file under `.zitadel/` that cannot be written because a directory it needs is a file is refused with `<path> cannot be written (ENOTDIR)` and a hint to remove that file. A file under `.zitadel/` that is not valid JSON is refused with its path and the line and column of the error, such as `.zitadel/branding/branding.json: cannot be parsed: invalid JSON at line 5, column 18`, and never with a piece of the file.
