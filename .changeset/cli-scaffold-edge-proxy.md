`setup` now scaffolds a production edge proxy for SPA frameworks (React, Vue, Solid, Svelte, Qwik, Angular). A SPA has no server runtime, so the same-origin `/__nextgen/*` proxy that injects the project secret must run as a platform edge function — the dev proxy each framework already scaffolds only covers local development. The CLI detects the deploy platform from the installed platform CLI (`wrangler`, `vercel`, `netlify`; a present `wrangler.*`/`vercel.json`/`netlify.toml` disambiguates when several are installed) and writes the matching entry: a Cloudflare Worker (`zitadel-edge-proxy.ts` + `wrangler.jsonc` with `run_worker_first`), a Vercel Edge Middleware (`middleware.ts` with a `/__nextgen` matcher), or a Netlify Edge Function (`netlify/edge-functions/zitadel-nextgen.ts`, auto-discovered via its inline `config.path`). Each platform's native edge primitive intercepts `/__nextgen/*` directly, so the handler's default path prefix matches with no rewrite. (Vercel uses middleware rather than an `api/` function because Vercel does not build `api/` functions for a static Vite SPA.) The backend URL is written to the env file that platform's dev server loads (`.dev.vars` for Cloudflare, `.env` for Netlify, `.env.local` for Vercel) and setup prints the `secret put`/`env add`/`env:set` command to push `ZITADEL_PROJECT_SECRET` to the platform store for production. The chosen target is persisted in `zitadel.json` so `eject` and `doctor` can manage the generated files. When no platform CLI is installed, nothing is scaffolded.
