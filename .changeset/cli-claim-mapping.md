`auth-method sso enable` and `setup` now map provider claims to user-schema properties. The standard OpenID Connect claims whose names match a property of the schema (`email`, `givenName`, `familyName`, `picture`, and the rest of the profile, email and phone claims whose scope the connection requests) are mapped by default, for Google and custom connections alike. To fill another property, repeat `--claim <property>=<claim>` (`--sso-claim` on `setup`); a claim the provider returns as a number, integer or boolean says so after a colon, as in `--claim staffNumber=employee_id:integer`. `--claim-scope` adds the scopes the claims need, and `--verified-claim <property>=<claim>` or `<property>=true` says how a unique property is verified. A claim you give replaces the default for its property (`--claim email=mail`), and a replaced default is no longer verified until `--verified-claim` says how. A claim fills one property and a property takes one claim, a claim's type has to fit the property's (a string cannot fill an integer), and a property the schema does not define is refused, all before a secret is asked for or a file written. Interactively, setup and `auth-method sso enable` now walk through the provider as one wizard: the questions for a new provider sit in a branch under the "Add sign-in with another service?" question, the OAuth redirect URI is shown just before the client ID is asked for, and the claims each provider fills by default are shown as a table of user attribute, claim and who verifies it. "Should any other claims be mapped from the provider?" then opens a branch for each claim you add: which claim to read, the type of value it is, the user attribute it maps to, the scope that makes the provider send it, and, for a unique attribute, whether the provider confirms it is verified. A connection file that already exists keeps its own mapping and the command warns that the claims were not applied. `--json` reports the mapping, the verification and the scopes of a connection it creates.
