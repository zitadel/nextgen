`setup` and `auth-method sso enable` now say what a provider's connection file maps. After a provider is enabled they print, in a box like the one `setup` ends with, the connection file's path, the claim mapping as user attribute → claim, what makes the email verified as a separate block, the scopes, whether the connection is only saved in the project or also applied to the server (neither is tested until a real sign-in), and what is still to do. `plan` ends with a box that lists its changes and what each connection it creates or changes maps. `--json` reports the same `claim_mapping`, `verified_claims` and `scopes`.

The claim mapping is also validated much more tightly. The server refuses a `claim_mapping` or `verified_claims` key that is empty or contains a dot, a `verified_claims` entry for a property `claim_mapping` does not map, a standard claim read without its scope (when the scopes are all standard ones), a verification that reads a claim that is not a boolean or that vouches for another claim, a claim name with a space around it, and a `subject_claim` that is a profile claim. `plan` and `apply` add "Did you mean" to a mapping target or verification key no schema defines, and refuse the mistakes that otherwise only show up at sign-in: a verification of a property that is not unique in any schema that lists the connection, a standard claim read without the scope that makes a provider return it, a standard claim whose type the target property cannot hold (such as `updated_at` into a string), a verification that reads a standard claim that is not a boolean, an email verified by a claim that vouches for another, a provider listed twice, a claim name with a space around it, a `subject_claim` that is a profile claim or an account name the user can change, a field the contract does not define (a misspelt `claim_maping`), and a user-creating step that neither asks for a required property (or the one people sign in by) nor has every provider map it. A connection scaffolded for a narrower set of scopes, or for a schema whose email is not unique, maps and verifies only what can work.
