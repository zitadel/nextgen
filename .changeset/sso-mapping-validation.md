`setup`, `auth-method sso enable` and `deploy --dry-run` now describe a provider's connection the same way, in a bordered box. It reads as sentences: one line per user attribute saying which claim fills it and, folded into the same line, what makes it verified; the scopes the connection requests; the attributes the signing-in schemas define that no claim fills yet, each marked required or optional rather than ordered to be mapped; and which user schemas sign in through the connection, so a mapping change says who it affects. `setup` and `enable` also say where the connection stands (saved in the project, or deployed to the server — neither tested until a real sign-in) and what is still to do. `--json` reports the same `claim_mapping`, `verified_claims` and `scopes`.

The CLI also validates the claim mapping much more tightly. `deploy` adds "Did you mean" to a mapping target or verification key no schema defines, and refuses the mistakes that otherwise only show up at sign-in: a standard claim whose type the target property cannot hold (such as `updated_at` into a string), a verification that reads a standard claim that is not a boolean, a provider listed twice, a claim name with a space around it, a `subject_claim` that is a profile claim or an account name the user can change, a field the contract does not define (a misspelt `claim_maping`), and a user-creating step that neither asks for a required property (or the one people sign in by) nor has every provider map it. One softer mistake warns rather than stops, so the deploy carries on: a custom connection that reads a standard claim without the scope that returns it. A catalog connection, whose scopes the CLI scaffolds, still fails on a missing scope. A connection scaffolded for a narrower set of scopes, or for a schema whose email is not unique, maps and verifies only what can work.
