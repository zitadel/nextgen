`setup` and `auth-method sso enable` now say what a provider's connection file maps. After a provider is enabled they print, in a box like the one `setup` ends with, the connection file's path, the claim mapping as user attribute → claim, what makes the email verified as a separate block, the scopes, whether the connection is only saved in the project or also deployed to the server (neither is tested until a real sign-in), and what is still to do. `deploy --dry-run` prints the same mapping box for every connection, after the diff. `--json` reports the same `claim_mapping`, `verified_claims` and `scopes`.

The CLI also validates the claim mapping much more tightly. `deploy` adds "Did you mean" to a mapping target or verification key no schema defines, and refuses the mistakes that otherwise only show up at sign-in: a standard claim whose type the target property cannot hold (such as `updated_at` into a string), a verification that reads a standard claim that is not a boolean, an email verified by a claim that vouches for another, a provider listed twice, a claim name with a space around it, a `subject_claim` that is a profile claim or an account name the user can change, a field the contract does not define (a misspelt `claim_maping`), and a user-creating step that neither asks for a required property (or the one people sign in by) nor has every provider map it. Two softer mistakes warn rather than stop, so the deploy carries on: a verification of a property that is not unique in any schema that lists the connection, which nothing reads today, and a custom connection that reads a standard claim without the scope that returns it. A catalog connection, whose scopes the CLI scaffolds, still fails on a missing scope. A connection scaffolded for a narrower set of scopes, or for a schema whose email is not unique, maps and verifies only what can work.
