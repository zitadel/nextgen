Add a custom OpenID Connect provider to the CLI. `zitadel sso enable --provider custom` takes a connection name (`--slug`), a sign-in button name (`--display-name`), an `--issuer` and optional `--scopes` (`openid` required, defaulting to `openid profile email`), and writes `.zitadel/idps/<slug>.json`, enables it on the user schema and adds it to every login flow, as it does for Google. The connection is identified by its slug rather than its issuer, so a Project can hold several connections to one issuer; a name already used for a connection to a different issuer is refused. `zitadel setup` offers the same as "another OpenID Connect provider", with `--sso custom` and `--sso-slug`, `--sso-display-name`, `--sso-issuer` and `--sso-scopes` for scripted runs. The connection maps the standard OpenID Connect claims the schema defines and trusts `email` only when the provider reports `email_verified`; other mappings are made by editing the file. Adding a second provider after `apply` no longer reports the conflict and registration steps as hand-edited because the platform filled in their empty `gates` and `sso_providers`. `@zitadel/config/idp` no longer exports `ISSUER_REQUIREMENT` or `isSupportedIssuer`; use `parseIssuer`, which returns the issuer or why it is refused. `idpProvider` and `IDP_PROVIDERS` now cover only the catalog's own providers, `IdpProvider.template` is `string | undefined` because a custom connection names no template, and `selectionSlug` is gone in favour of `providerOf(selection).slug`.
