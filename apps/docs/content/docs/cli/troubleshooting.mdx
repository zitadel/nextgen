## Local server is not running

`setup --server local`, `console`, and any other command run with `--server local` report `E_LOCAL_SERVER_NOT_RUNNING` when the local runtime is stopped. `plan` and `apply` use the server URL setup wrote into `zitadel.json` instead, so against a stopped local server `apply` fails with `E_NETWORK` (`ECONNREFUSED`), and `plan` runs without the server's current state. In each case, start the local runtime:

```sh
npx @zitadel/cli@alpha start
```

Then retry the command.

## Port is in use

If `start` or `doctor` reports `E_PORT_IN_USE`, the runtime port already has a listener. If it is a runtime the CLI started earlier with the default binary backend, possibly in another directory, stop all of those (macOS and Linux only):

```sh
npx @zitadel/cli@alpha stop --all
```

`stop --all` does not stop a Docker runtime; run `stop` in the directory that runtime was started from. Otherwise, stop the process that holds the port, or choose another port:

```sh
npx @zitadel/cli@alpha start --port 8081
```

## JSON output looks mixed with installer logs

Capture stdout and stderr separately. The JSON envelope is on stdout; package-manager progress belongs on stderr.

## Browser proof stops at the form

A rendered login or registration form is not enough. Complete registration, logout, login, and signed-in profile verification in a real browser.

## Old localhost passkeys still appear

Browser and OS passkeys for `localhost` can outlive `zitadel reset --force`, deleted app folders, and new local projects. If the passkey picker shows stale local accounts, remove the old `localhost` passkeys from your browser or operating system credential manager.

Password managers can also keep their save or update sheet open after the app redirects to the signed-in profile. An `Update Existing` prompt usually means the manager found an old `localhost` item with the same account label. Update it, save a new item, or delete the stale local passkey before retrying.
