---
title: Test your app's sign-in
description: Run end-to-end tests of your app against a real local Zitadel with @zitadel/testing, its Playwright fixtures and login helpers.
---

`@zitadel/testing` is the test kit for apps that use Zitadel. It boots a real Zitadel server from your test run, with SQLite and without Docker. It creates a project with the default login flow, then seeds users and sessions through the API. Its Playwright fixtures and helpers drive the real login in a browser.

With it you can:

- Sign a seeded user in through your app's own login page, with a password or a passkey.
- Start a test already signed in, to test the pages behind the sign-in.
- Call your app's backend as a signed-in user, without a browser.
- Register a new user through the real sign-up flow.

The kit is in preview: until 1.0.0, a minor version can change its API, and its release note marks that **Breaking:**. It runs on macOS and Linux only. The full API is in its [README](https://github.com/zitadel/nextgen/tree/main/packages/testing#readme).

## Before you start

- **An app from `zitadel setup`** ([Quickstart](/docs/get-started/quickstart)). The example below is a Next.js app; [Other frameworks](#other-frameworks) says what changes for the rest.
- **Node.js 24 or later**, as for the CLI.

The kit does not use the project `setup` created or the runtime `zitadel start` runs. Each test run boots its own Zitadel server on a port you choose and creates a fresh project in it. When the run ends, the kit stops that server and deletes its data.

## Install the kit

Install the kit and Playwright as dev dependencies, then Playwright's Chromium:

```sh
npm install --save-dev @zitadel/testing@latest @playwright/test
npx playwright install chromium
```

The kit runs the `zitadel` CLI, which finds the `@zitadel/server` binary on its own. There is no binary path or environment variable to set.

Add the kit's files and Playwright's output to `.gitignore`. `.zitadel-testing/` holds the test server's handshake file, which carries the test project's secret:

```text title=".gitignore"
.zitadel-testing/
test-results/
playwright-report/
```

## Configure Playwright

`withZitadel()` returns the `webServer` entries that boot the test server and then your app's dev server against it. It hands the app the test server's URL, project ID and secret through environment variables, which win over the values `setup` wrote to `.env.local`:

```ts title="playwright.config.mts"
import { defineConfig } from "@playwright/test";
import { nextAppEnv, withZitadel } from "@zitadel/testing/playwright";

const appOrigin = "http://localhost:3100";

export default defineConfig({
  testDir: "./e2e",
  use: { baseURL: appOrigin },
  ...withZitadel({
    configDir: import.meta.dirname,
    port: 8092,
    appOrigin,
    app: {
      command: ["npx", "next", "dev", "--hostname", "localhost", "--port", "3100"],
      cwd: import.meta.dirname,
      readyPath: "/login",
      env: nextAppEnv,
    },
  }),
});
```

- `port` is the test server's port. It must be free, so pick one your local runtime does not use (that one listens on 8080 by default).
- `appOrigin` is where the test run serves your app. The kit registers it as the test project's origin. Use a port other than your dev server's, so both can run at once.
- `readyPath` is a page Playwright polls until the app answers.
- `nextAppEnv` maps the test server to the variables a Next.js app reads.

The `.mts` extension makes Node load the file as an ES module, which `import.meta.dirname` needs. Without it, an app whose `package.json` has no `"type": "module"` fails to load the config.

## Sign a seeded user in

`seed.user()` creates a user with a unique email and a password, ready to sign in. `loginWithPassword()` fills the login component's identifier and password steps:

```ts title="e2e/login.spec.ts"
import { expect, loginWithPassword, test } from "@zitadel/testing/playwright";

test("a seeded user signs in with their password", async ({ page, seed }) => {
  const user = await seed.user();

  await page.goto("/login");
  await loginWithPassword(page, user);

  await expect(page).toHaveURL(/\/profile/);
});
```

Run it:

```sh
npx playwright test
```

The first run takes longest: the test server creates its database, then your app's dev server compiles. Each test gets its own user, so tests run in parallel against the one test server.

The helpers find the login component's controls by their automation hooks, not by their text, so they keep working when you change copy or locale. They never check your app's state: assert what your app shows after the sign-in yourself. `registerWithPassword()` and `registerWithPasskey()` drive the sign-up flow the same way, with an unused email from `seed.identity()`.

## Start a test signed in

Most tests of your app's pages should not test the sign-in again. The `authenticatedPage` fixture seeds a user, signs it in without a browser, and puts the session cookie into a page of its own:

```ts title="e2e/profile.spec.ts"
import { expect, test } from "@zitadel/testing/playwright";

test("a signed-in user stays on the profile page", async ({ authenticatedPage }) => {
  const { page } = authenticatedPage;

  await page.goto("/profile");

  await expect(page).toHaveURL(/\/profile/);
});
```

`setup` protects `/profile`, so a signed-out visitor is sent to `/login` instead. `authenticatedPage.user` is the seeded user, for assertions on what your page shows. The default `page` fixture stays signed out, for tests of the sign-in itself. `authenticatedPage` needs `use.baseURL`, which names the origin the cookie is for.

## Call your backend as a signed-in user

`seed.session()` seeds a user and returns its session token, without a browser. Send it as the session cookie your app reads. `sessionCookieName()` names that cookie for your project and origin:

```ts title="e2e/api.spec.ts"
import { expect, sessionCookieName, test } from "@zitadel/testing/playwright";

test("the API answers a signed-in user", async ({ request, seed, zitadel, baseURL }) => {
  const { sessionToken } = await seed.session();
  const cookie = `${sessionCookieName(zitadel.handle.projectId, baseURL)}=${sessionToken}`;

  const response = await request.get("/api/<your-route>", { headers: { cookie } });

  expect(response.ok()).toBe(true);
});
```

Replace `/api/<your-route>` with a route of your app that requires a sign-in.

## Test passkeys

The `passkey` fixture attaches a virtual authenticator to the page, so registering and signing in with a passkey complete without an operating-system dialog:

```ts title="e2e/passkey.spec.ts"
import { expect, registerWithPasskey, test } from "@zitadel/testing/playwright";

test("a new user registers a passkey", async ({ page, seed, passkey }) => {
  const who = seed.identity();

  await page.goto("/login");
  await registerWithPasskey(page, { email: who.email });

  await expect.poll(() => passkey.credentialCount()).toBe(1);
});
```

`seed.identity()` returns an unused email and password and creates nothing, so the flow under test creates the user. `loginWithPasskey()` signs a user back in.

- The virtual authenticator works in Chromium only.
- It belongs to the page: register and sign in again on the same page. To sign out in between, clear the context's cookies instead of opening a new context.
- Serve the app on `http://localhost` or HTTPS. An IP address such as `127.0.0.1` is not a valid origin for passkeys.

## Other frameworks

`nextAppEnv` maps the test server to the variables a Next.js app reads. For another framework, pass a template of your own: an object from each variable name your app reads to a field of the test server's handle. `setup` wrote those names to `.env.local`: `ZITADEL_URL`, `ZITADEL_PROJECT_ID`, `ZITADEL_PROJECT_SECRET`, and for most frameworks a public copy of the project ID, such as `VITE_ZITADEL_PROJECT_ID`:

```ts
import type { AppEnvTemplate } from "@zitadel/testing/playwright";

const viteAppEnv: AppEnvTemplate = {
  ZITADEL_URL: "baseUrl",
  ZITADEL_PROJECT_ID: "projectId",
  VITE_ZITADEL_PROJECT_ID: "projectId",
  ZITADEL_PROJECT_SECRET: "projectSecret",
};
```

Set `app.command` to your framework's dev server on the port of `appOrigin`, and `app.readyPath` to your sign-in page. A template that names a field the handle does not carry fails the run with that variable's name.

To use the kit with a runner other than Playwright, start the test server yourself with `startLocalZitadel()` from `@zitadel/testing`. It returns the same seeding functions ([README](https://github.com/zitadel/nextgen/tree/main/packages/testing#api)).

## Limits

- **Password flows only, without a browser.** `authenticatedPage` and `seed.session()` complete the default password flows. A step that asks for anything else, such as a code or a second factor, fails with the step's name. Drive those flows in the browser instead.
- **No email or SMS codes.** The kit cannot read a verification code yet, so a flow that sends one cannot run to the end.
- **One test server per process.** The kit's API client keeps its credentials per process. Do not call two test servers from one process; Playwright's workers are separate processes.
- **macOS and Linux.** Windows is not supported yet.

## When a run fails

- **The test server does not boot.** Another process holds its `port`: choose another, or stop what holds it. `npx @zitadel/cli@latest stop --all` stops every runtime the CLI started, including ones a crashed run left behind.
- **Playwright says the app's URL is already in use.** The kit always starts the app itself. Stop the dev server on `appOrigin`'s port, or move `appOrigin` to a free port.
- **You need the server's log.** Set `zitadel: { keep: true }` in `withZitadel()`'s options to keep the test server's directory. Its log is `.zitadel/local/server.log` in it. A failed boot always keeps the directory and prints its path.
