The login component ships with a built-in template that follows your project without any files in your repo. Its look comes from your app. Style it from your own stylesheet with [`--zl-*` tokens and CSS parts](#style-the-login-from-your-app), and put any page layout around it in your own code: a split screen, a brand pane, marketing copy.

To change the login's *structure*, eject its template with `branding eject`. Ejecting means you take ownership of the template. The command copies a starter design into `.zitadel/branding/`. `zitadel setup` does not create that folder. Once you deploy it, the login renders your files ([Eject a design](#eject-a-design)).

## Style the login from your app

Two hooks reach inside the login's shadow DOM, the isolated tree its markup lives in, from your app's stylesheet. Both are stable across releases. Both win over the branding your project publishes, so the login matches your app without a branding revision.

Put these rules in a stylesheet that loads on every page, not in a CSS module or a scoped `<style>`.

- Next.js: in an app that `zitadel setup` or `create-next-app` created, the root layout (`app/layout.tsx`) already imports `app/globals.css`. With a `src` folder, both sit under `src/app/`. In another app, use the stylesheet your root layout imports.
- Nuxt: `zitadel setup` creates no global stylesheet. Create `app/assets/css/main.css`, or `assets/css/main.css` in an app without an `app/` folder. Then add a `css` key to `nuxt.config.ts`. Keep every key the file already has:

```ts
export default defineNuxtConfig({
  // Keep the keys your file already has, such as `modules` and `vue`.
  css: ["~/assets/css/main.css"],
});
```

### Tokens

Set `--zl-*` custom properties on `zitadel-login`. These names are stable:

| What it styles | Tokens |
| --- | --- |
| Primary button | `--zl-primary`, `--zl-primary-foreground` |
| Page and card | `--zl-background`, `--zl-card`, `--zl-popover` |
| Text | `--zl-foreground`, `--zl-muted-foreground`, `--zl-card-foreground`, `--zl-popover-foreground` |
| Muted surfaces | `--zl-muted`, `--zl-secondary`, `--zl-secondary-foreground`, `--zl-accent`, `--zl-accent-foreground` |
| Edges | `--zl-border` (the card and alerts), `--zl-input` (fields and other controls) |
| Links | `--zl-link` |
| Status | `--zl-success`, `--zl-warning`, `--zl-destructive` |
| Type | `--zl-font-family-sans`, `--zl-font-family-heading`, `--zl-text-{xs,sm,base,lg,xl}-size`, `--zl-text-{xs,sm,base,lg,xl}-leading` |
| Shape | `--zl-radius-{xs,sm,md,lg,xl}`, `--zl-spacing-4`, `--zl-spacing-8`, `--zl-logo-scale` |

Other `--zl-*` variables in the component's styles are internal and can change in any release.

### CSS parts

For what no token covers, such as border widths, shadows or letter case, style the login's parts with `::part()`. A part's name is the inner component's tag without `zl-`, a hyphen, and the part: the `card` part of `zl-card` is `zitadel-login::part(card-card)`.

| Component | Parts |
| --- | --- |
| `zl-card` | `card-card`, `card-header`, `card-body`, `card-footer` |
| `zl-field` | `field-root`, `field-label`, `field-label-row`, `field-forgot-link`, `field-input-wrap`, `field-input`, `field-trailing-icon`, `field-trailing-action`, `field-password-toggle`, `field-help`, `field-success`, `field-error` |
| `zl-button` | `button-root`, `button-spinner` |
| `zl-alert` | `alert-alert`, `alert-icon`, `alert-body`, `alert-title`, `alert-message`, `alert-detail`, `alert-link`, `alert-close` |
| `zl-checkbox` | `checkbox-field`, `checkbox-root`, `checkbox-input`, `checkbox-box`, `checkbox-face`, `checkbox-check`, `checkbox-label`, `checkbox-error` |
| `zl-select` | `select-root`, `select-label`, `select-field`, `select-native`, `select-trigger`, `select-listbox`, `select-option`, `select-error` |
| `zl-sso-providers` | `sso-providers-root`, `sso-providers-divider`, `sso-providers-list`, `sso-providers-provider`, `sso-providers-provider-button` |
| `zl-page-shell` | `page-shell-shell`, `page-shell-header`, `page-shell-main`, `page-shell-footer` |
| `zl-account`, `zl-avatar`, `zl-pill` | `account-chip`, `avatar-avatar`, `pill-pill` |

The login also names its own parts directly: `form`, `paired-identifier`, `attribution`, and `attribution-mark`.

A flat, hard-edged look, for example, needs both hooks:

```css
zitadel-login {
  --zl-font-family-sans: "Space Mono", ui-monospace, monospace;
  --zl-font-family-heading: "Space Mono", ui-monospace, monospace;
  --zl-primary: #0a0a0a;
  --zl-primary-foreground: #c6ff00;
  --zl-radius-xs: 0;
  --zl-radius-sm: 0;
  --zl-radius-md: 0;
  --zl-radius-lg: 0;
  --zl-radius-xl: 0;
}

zitadel-login::part(card-card) {
  border: 3px solid #0a0a0a;
  box-shadow: 6px 6px 0 #0a0a0a;
}

zitadel-login::part(button-root) {
  text-transform: uppercase;
}
```

The example sets `--zl-font-family-heading` to the same font as `--zl-font-family-sans`. The card title, field labels and alert titles use the heading font. Without it, they keep the default font. The branding `typography.font_family` sets both tokens for the same reason.

The login draws its own card, so give that card your frame through `card-card` rather than wrapping the element in a second box.

The example applies the same stylesheet to a live login, which runs against a mock of the flow API in your browser. Change a value, and the stylesheet under the login shows what your app would write:

<StyledLoginStory.WithControl />

`<zitadel-session>` and `<zitadel-logout>` take the same tokens but expose no parts: frame them from your own markup.

### Light and dark themes

The login renders in a light or a dark theme. It marks the active one on the element as `data-theme="light"` or `data-theme="dark"`.

A token you set on `zitadel-login` applies to both themes. When you change a surface, change its text colour with it. Set `--zl-card` together with `--zl-card-foreground`, or the card text can become hard to read in one theme.

To give one theme its own values, select on `data-theme`:

```css
zitadel-login {
  --zl-primary: #4f46e5;
  --zl-primary-foreground: #ffffff;
}

zitadel-login[data-theme="dark"] {
  --zl-card: #111827;
  --zl-card-foreground: #f9fafb;
}
```

The login picks its theme in this order:

1. The element's `theme` attribute: `light`, `dark` or `auto`. `auto` follows the visitor's operating system setting.
2. `theme.mode` in your branding ([Brand the light and dark themes](#brand-the-light-and-dark-themes)).
3. The variant's default: `variant="page"` is dark, `variant="widget"` is `auto`.

A branding that sets only one side, such as only `theme.dark`, always shows that side.

When `zitadel setup` adds sign-in pages to an existing Next.js or Nuxt app, the pages use `variant="widget"` and also set `theme="auto"`. That attribute wins over `theme.mode`. Remove `theme="auto"` from those pages to let your branding decide. Setup sets no `theme` on any other page it writes.

With `variant="widget"`, the theme changes only the login's card. The page around the card is your app's, so set its colours in your own stylesheet. With `variant="page"`, the login paints the whole page in the theme.

`<zitadel-session>` and `<zitadel-logout>` do not read your branding, so `theme.mode` does not reach them. Set their `theme` attribute yourself.

## Put the login in your own page

A page with its own heading and layout around the login needs three props, on top of the tokens and parts above:

- `variant="widget"` sizes the login to its content and paints no page around it. `page` takes the whole viewport instead.
- `suppressHeader` hides the login's own title and subtitle, so the page's heading is the only one a visitor sees. Screen readers still announce the step.
- `onFlowStep` gives the page every step the login shows, including the first. Title the page from `step.purpose`, not from the `purpose` you passed: a sign-in whose email has no account carries on as a sign-up, and a sign-up whose email has one carries on as a sign-in.

In React or Next.js:

```tsx
"use client";

import { useState } from "react";
import { ZitadelLogin } from "@zitadel/sdk-next/components";

const titles = { login: "Welcome back.", register: "Create your account." };

export function SignIn({ project, purpose }) {
  const [current, setCurrent] = useState(purpose);
  return (
    <main className="auth-page">
      <h1>{titles[current] ?? titles.login}</h1>
      <ZitadelLogin
        project={project}
        purpose={purpose}
        variant="widget"
        suppressHeader
        onFlowStep={({ step }) => setCurrent(step.purpose ?? purpose)}
      />
    </main>
  );
}
```

The other SDKs take the same props. The step callback follows each framework's naming: `@flowStep` in [Vue](/docs/sdks/vue#props-and-events), `(flowStep)` in [Angular](/docs/sdks/angular#props-and-events), `onFlowStep$` in [Qwik](/docs/sdks/qwik#props-and-events), and `onFlowStep` in the rest. To change the login's own wording, such as a field's label, use the `locales` prop ([Customize the login text](/docs/guides/customize-copy)).

## Starter designs

| Design | Layout | Uses logo |
| --- | --- | --- |
| `centered` | The default card, ejected as-is | yes |
| `minimal` | The same form without card chrome | no |

Both render every step of your login flow: sign-in, registration, passkey ceremonies and their error states. They template the flow engine's step responses rather than individual screens.

## Eject a design

`zitadel setup` never applies a design: it embeds the maintained login component and publishes no branding revision. Eject the template at any time. Run the command in a project that `zitadel setup` created. In any other directory it fails with `E_VALIDATION`: "This directory is not a Zitadel project".

```sh
npx @zitadel/cli@latest branding eject
```

`branding eject` offers the two starter designs above, then scaffolds `.zitadel/branding/` locally. Nothing is uploaded until you deploy. Pass `--design minimal` to choose a design without the prompt. A non-interactive run uses `centered`.

```text
Ejected the <design> design into .zitadel/branding/
```

With `--json`, `data.design` names the design and `data.files_written` lists the files. If `branding.json` or `login.liquid` already exists, the command stops with `E_CONFLICT`. Pass `--force` to replace them, or edit the existing files. The scaffold holds:

- `branding.json`: the descriptor, with the layout, brand asset URLs and the template reference.
- `login.liquid`: the LiquidJS template the login renders for every step.
- `README.md`: the template rules and workflow, kept next to the files.

## Add your branding

Brand assets live in `branding.json` and must be hosted `https://` URLs. While you develop, images may also use `http://` on `localhost`, a `127.x.x.x` address, or `[::1]`; the login shows them only when its own page runs on one of those hosts. The CLI validates the URLs before it deploys, and the server rejects anything else:

```json
{
  "$schema": "../meta/branding.json",
  "layout": "centered",
  "logo_url": "https://cdn.example.com/logo.svg",
  "typography": {
    "font_family": "Inter, ui-sans-serif, sans-serif",
    "font_url": "https://cdn.example.com/fonts/inter.css"
  },
  "liquid_template": { "$file": "./login.liquid" }
}
```

Each design decides which images it shows: `centered` shows the logo, `minimal` shows none, and neither shows `hero_url`. A URL the design doesn't use is stored but not shown, and `deploy` still checks it.

`typography.font_family` sets the typeface for body and headings; include a generic family as a fallback. `typography.font_url` is a stylesheet that loads the face. It needs a `font_family`, must be `https://`, and is loaded only when the login runs as `variant="page"`. Setup generates page-variant sign-in pages only when it creates the Next.js or Nuxt app itself, in an empty directory. In a Next.js or Nuxt app that already exists, even a new one, and in every SPA template, the login runs as `variant="widget"`. Load the font from your own page there.

Without `font_url` the login loads no font of its own: it renders in Arimo where the browser already has it, and in the system font otherwise, so it sends no request to a font host. A `font_url` on a third-party host such as Google Fonts sends every visitor's IP address to that host, which under the GDPR can require their consent. Serve the stylesheet and font files from your own domain to avoid that.

### Brand the light and dark themes

`theme` in `branding.json` holds a look for each theme:

- `theme.mode` picks the theme: `light`, `dark` or `auto`. The element's `theme` attribute wins over it ([Light and dark themes](#light-and-dark-themes)).
- `theme.light` and `theme.dark` each take a `logo_url` and a `palette`. A side's palette applies only to that theme.

```json
{
  "$schema": "../meta/branding.json",
  "layout": "centered",
  "theme": {
    "mode": "auto",
    "light": {
      "logo_url": "https://cdn.example.com/logo-on-light.svg",
      "palette": {
        "primary": "#4f46e5",
        "on_primary": "#ffffff",
        "background": "#f9fafb",
        "surface": "#ffffff",
        "text": "#111827"
      }
    },
    "dark": {
      "logo_url": "https://cdn.example.com/logo-on-dark.svg",
      "palette": {
        "primary": "#818cf8",
        "on_primary": "#111827",
        "background": "#030712",
        "surface": "#111827",
        "text": "#f9fafb"
      }
    }
  },
  "liquid_template": { "$file": "./login.liquid" }
}
```

`surface` colours the card. `background` colours the page around the card, which you see only with `variant="page"`. The create operation in the [branding API reference](/docs/reference/api/branding) lists every palette key.

Set a logo on both sides or on neither. A side without its own `logo_url` shows no logo, even when the other side has one. The top-level `logo_url` applies only when neither side sets one.

`deploy --dry-run` checks that the top-level `logo_url` and `hero_url` load. It does not check the logos under `theme`, so open the login in both themes to see them.

## Publish your design as a revision

Branding follows the same loop as schemas and flows:

```sh
npx @zitadel/cli@latest deploy --dry-run
npx @zitadel/cli@latest deploy
```

`deploy --dry-run` validates the descriptor and the template (LiquidJS parse, banned patterns, required tags) and shows the diff. `deploy` publishes it as part of the release. Every publish creates an immutable revision, so there is no in-place update. To roll back, deploy an earlier release ([Releases, deployments and rollback](/docs/guides/deploy#releases-deployments-and-rollback)).

A login that starts after the release is deployed shows the revision; one already open keeps the release it started with until it ends. To check, reload your app: the login now renders your template. `deployment list --live` confirms which release is live ([Deploy](/docs/guides/deploy#check-that-it-is-live)).

The scaffolded `README.md` in `.zitadel/branding/` documents the template rules (compose `zl-*` components, no `<script>` or `<style>` tags or inline event handlers, copy through translation keys).

## Decide whether to eject

An ejected template is yours: it stops receiving improvements to the built-in designs. Eject when you want to change the login's structure and look. To change only the wording, the `locales` prop does that without touching templates ([Customize the login text](/docs/guides/customize-copy)). Staying on the built-in template costs nothing, and `branding eject` is always one command away.
