You can restyle the login component from your app, or change its structure. The login component ships with a built-in template that follows your project and needs no files in your repo.

Its look comes from your app. Style it from your own stylesheet with [`--zl-*` tokens and CSS parts](#style-the-login-from-your-app). Put any page layout around it in your own code, such as a split screen, a brand pane or marketing copy.

To change the login component's *structure*, you take ownership of its template. This is called ejecting a design: the CLI copies a starter design into `.zitadel/branding/`. Once you deploy it, the login renders your files.

## Style the login from your app

Two hooks reach inside the login's shadow DOM, the isolated part of the page it renders in, from your app's stylesheet. Both hooks are stable across releases. Both win over the branding your project publishes, so the login matches your app without a branding revision.

### Tokens

Set `--zl-*` custom properties on `zitadel-login`. These names are stable:

| What it styles | Tokens |
| --- | --- |
| Primary button | `--zl-primary`, `--zl-primary-foreground` |
| Page and card | `--zl-background`, `--zl-card`, `--zl-popover` |
| Text | `--zl-foreground`, `--zl-muted-foreground`, `--zl-card-foreground`, `--zl-popover-foreground` |
| Muted surfaces | `--zl-muted`, `--zl-secondary`, `--zl-secondary-foreground`, `--zl-accent`, `--zl-accent-foreground` |
| Edges | `--zl-border` (the card and alerts), `--zl-input` (fields and other controls) |
| Links | `--zl-link` |
| Status | `--zl-success`, `--zl-warning`, `--zl-destructive` |
| Type | `--zl-font-family-sans`, `--zl-font-family-heading`, `--zl-text-{xs,sm,base,lg,xl}-size`, `--zl-text-{xs,sm,base,lg,xl}-leading` |
| Shape | `--zl-radius-{xs,sm,md,lg,xl}`, `--zl-spacing-4`, `--zl-spacing-8`, `--zl-logo-scale` |

Other `--zl-*` variables in the component's styles are internal and can change in any release.

### CSS parts

For what no token covers, such as border widths, shadows or letter case, style the login's parts with `::part()`. A part's name is the inner component's tag without `zl-`, then a hyphen, then the part. For example, the `card` part of `zl-card` is `zitadel-login::part(card-card)`.

| Component | Parts |
| --- | --- |
| `zl-card` | `card-card`, `card-header`, `card-body`, `card-footer` |
| `zl-field` | `field-root`, `field-label`, `field-label-row`, `field-forgot-link`, `field-input-wrap`, `field-input`, `field-trailing-icon`, `field-trailing-action`, `field-password-toggle`, `field-help`, `field-success`, `field-error` |
| `zl-button` | `button-root`, `button-spinner` |
| `zl-alert` | `alert-alert`, `alert-icon`, `alert-body`, `alert-title`, `alert-message`, `alert-detail`, `alert-link`, `alert-close` |
| `zl-checkbox` | `checkbox-field`, `checkbox-root`, `checkbox-input`, `checkbox-box`, `checkbox-face`, `checkbox-check`, `checkbox-label`, `checkbox-error` |
| `zl-select` | `select-root`, `select-label`, `select-field`, `select-native`, `select-trigger`, `select-listbox`, `select-option`, `select-error` |
| `zl-sso-providers` | `sso-providers-root`, `sso-providers-divider`, `sso-providers-list`, `sso-providers-provider`, `sso-providers-provider-button` |
| `zl-page-shell` | `page-shell-shell`, `page-shell-header`, `page-shell-main`, `page-shell-footer` |
| `zl-account`, `zl-avatar`, `zl-pill` | `account-chip`, `avatar-avatar`, `pill-pill` |

The login also names its own parts directly: `form`, `paired-identifier`, `attribution` and `attribution-mark`.

A flat, hard-edged look, for example, needs both hooks:

```css
zitadel-login {
  --zl-font-family-sans: "Space Mono", ui-monospace, monospace;
  --zl-primary: #0a0a0a;
  --zl-primary-foreground: #c6ff00;
  --zl-radius-xs: 0;
  --zl-radius-sm: 0;
  --zl-radius-md: 0;
  --zl-radius-lg: 0;
  --zl-radius-xl: 0;
}

zitadel-login::part(card-card) {
  border: 3px solid #0a0a0a;
  box-shadow: 6px 6px 0 #0a0a0a;
}

zitadel-login::part(button-root) {
  text-transform: uppercase;
}
```

The login draws its own card. Give that card your frame through `card-card` instead of wrapping the element in a second box.

The example applies the same stylesheet to a live login. The login runs against a mock of the flow API in your browser. Change a value, and the stylesheet under the login shows what your app would write:

<StyledLoginStory.WithControl />

`<zitadel-session>` and `<zitadel-logout>` take the same tokens but expose no parts. Frame them from your own markup.

## Starter designs

| Design | Layout | Uses logo |
| --- | --- | --- |
| `centered` | The default card, ejected as-is | yes |
| `minimal` | The same form without card chrome | no |

Both render every step of your login flow, including sign-in, registration, passkey steps and their error states. They template the flow engine's step responses, not individual screens.

## Eject a design

Ejecting copies a starter design into your repo, so you own the template from then on. `zitadel setup` never sets a design. It embeds the maintained login component and publishes no branding revision. You can eject at any time:

```sh
npx @zitadel/cli@latest branding eject
```

`branding eject` offers the two starter designs above, then creates `.zitadel/branding/` locally. Nothing is uploaded until you deploy. It holds three files:

- `branding.json`: the descriptor, with the layout, the brand asset URLs and the template reference.
- `login.liquid`: the LiquidJS template the login renders for every step.
- `README.md`: the template rules and workflow, kept next to the files.

## Add your branding

Brand assets live in `branding.json` and must be hosted `https://` URLs. While you develop, images may also use `http://` on `localhost`, a `127.x.x.x` address or `[::1]`. The login shows them only when its own page runs on one of those hosts. The CLI validates the URLs before it deploys, and the server rejects anything else:

```json
{
  "$schema": "../meta/branding.json",
  "layout": "centered",
  "logo_url": "https://cdn.example.com/logo.svg",
  "typography": {
    "font_family": "Inter, ui-sans-serif, sans-serif",
    "font_url": "https://cdn.example.com/fonts/inter.css"
  },
  "liquid_template": { "$file": "./login.liquid" }
}
```

Each design decides which images it shows. `centered` shows the logo, `minimal` shows none, and neither shows `hero_url`. A URL the design doesn't use is stored but not shown, and `deploy` still checks it.

`typography.font_family` sets the typeface for body and headings. Include a generic family as a fallback. `typography.font_url` is a stylesheet that loads the face. It needs a `font_family` and must be `https://`. The login loads it only when it runs as `variant="page"`.

Setup generates page-variant sign-in pages only when it creates the Next.js or Nuxt app itself, in an empty directory. In a Next.js or Nuxt app that already exists, even a new one, and in every SPA template, the login runs embedded in your own page. Load the font from your own page there.

Without `font_url`, the login loads no font of its own. It renders in Arimo where the browser already has it, and in the system font otherwise, so it sends no request to a font host.

A `font_url` on a third-party host such as Google Fonts sends every visitor's IP address to that host. Under the GDPR, that can require their consent. Serve the stylesheet and font files from your own domain to avoid that.

## Publish your design

Branding follows the same loop as schemas and flows:

```sh
npx @zitadel/cli@latest deploy --dry-run
npx @zitadel/cli@latest deploy
```

`deploy --dry-run` validates the descriptor and the template (LiquidJS parse, banned patterns, required tags) and shows the diff. `deploy` publishes it as part of the release.

Every publish creates an immutable revision. There is no in-place update. To roll back, deploy an earlier release ([Releases, deployments and rollback](/docs/guides/deploy#releases-deployments-and-rollback)). The live login picks up the newest revision on its next step response.

The generated `README.md` in `.zitadel/branding/` documents the template rules: compose `zl-*` components, use no `<script>` or `<style>` tags or inline event handlers, and write copy through translation keys.

## Decide whether to eject

An ejected template is yours, and it stops receiving improvements to the built-in designs. Eject when you want to change the login's structure and look.

To change only the wording, use the `locales` prop. It needs no template ([Customize the login text](/docs/guides/customize-copy)). Staying on the built-in template costs nothing, and `branding eject` is always one command away.
