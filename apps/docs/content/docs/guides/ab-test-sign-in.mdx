---
title: A/B test your sign-in
description:
  Serve two versions of your sign-in configuration to different visitors on
  the same origin, measure which works better, and keep the winner.
---

An A/B test of the sign-in serves two versions of its configuration side by
side, for example a passkey-first flow against a password-first one. Each
version is a [release](/docs/concepts/releases-and-deployments#release). Both
are deployed to your production origin, and your app
[pins](/docs/guides/pin-a-release) each visitor to one of them.

Your app decides who gets which version, and measures which one works better.
Zitadel serves the release each visitor's sign-in pins, and records it on the
sign-in's events.

## Before you start

- **Pinning set up.** Follow [Pin your app to a release](/docs/guides/pin-a-release)
  first; this guide uses the same build variables and `configureZitadel`.
- **A way to split visitors.** A cookie your app sets, or the experiment tool
  you already use. The assignment must stick to a visitor.
- **The two versions as two commits of `.zitadel/`.** This guide keeps the
  current configuration on `main` as version A and the change you test on a
  branch as version B.

## Deploy both versions

Deploy version B first, then version A. Each deploy prints its release ID:

```sh
git switch sign-in-variant-b
npx @zitadel/cli@latest deploy -m "A/B test: variant B"
git switch main
npx @zitadel/cli@latest deploy -m "A/B test: variant A"
```

```text
Release 9f2c1a7b4e83 is now live on https://app.example.com.
NEXT_PUBLIC_ZITADEL_RELEASE=rel_01KB3F8N2P9S5WQV
```

Version A deployed last, so it stays the release served to anything that does
not pin: other clients, and visitors on an older build. Both releases are now
in the origin's deployment history, so both can be pinned there. Check with:

```sh
npx @zitadel/cli@latest deployment list --origin https://app.example.com
```

## Build the app with both release IDs

Give the build both IDs:

```sh
NEXT_PUBLIC_ZITADEL_RELEASE_A=<release id of version A>
NEXT_PUBLIC_ZITADEL_RELEASE_B=<release id of version B>
```

## Pin each visitor to their version

Assign the visitor before the login component starts, and pass that version's
release to `configureZitadel`. With Next.js, reading the variant from a cookie
your app or your experiment tool set:

```tsx
"use client";
import { configureZitadel } from "@zitadel/sdk-next/client";

const variant = document.cookie.includes("signin_variant=b") ? "b" : "a";

configureZitadel({
  projectId: process.env.NEXT_PUBLIC_ZITADEL_PROJECT_ID!,
  proxyPath: "/__nextgen",
  release:
    variant === "b"
      ? process.env.NEXT_PUBLIC_ZITADEL_RELEASE_B
      : process.env.NEXT_PUBLIC_ZITADEL_RELEASE_A,
});
```

A sign-in that has started stays on its version: the flow keeps the deployment
it started on, even if the visitor's cookie changes mid-way.

## Check that both versions are served

1. Open the sign-in page in two browser profiles, one with
   `signin_variant=b` set and one without.
2. Each shows its version's first step.
3. In the developer tools, each `POST` to `/__nextgen/…/flows` carries its own
   `X-Zitadel-Release`.

## Measure the outcome

Measure success the way your app already does: it knows which version each
visitor got, so its analytics can compare sign-ups, completed sign-ins or
anything else you care about.

Zitadel's events are a second source that needs no change to your app. Every
event a sign-in emits carries the `release_id` and `deployment_id` that served
it. List one version's events, for example its failed checks:

```sh
npx @zitadel/cli@latest event list --filter release_id=<release id of version B> --filter event_type=auth.check.failed
```

Compare the counts with version A's. The API equivalent is
`GET /events?release_id=<release id>`.

## Keep the winner

1. **Ship the winner.** If B wins, merge its branch and run `zitadel deploy`.
   Unchanged content is the same release, so this deploys version B's release
   again and makes it what the origin serves. If A wins, nothing needs
   deploying.
2. **End the split.** Remove the assignment and build the app with one
   `NEXT_PUBLIC_ZITADEL_RELEASE`, or none.
3. **Revoke the loser** once no build pins it and nothing serves it:
   `zitadel release revoke <release id>`. A tab still open on an old build then
   gets `rel.revoked` and needs a reload, so do this after the new build is
   live.

Until you revoke it, the losing version stays pinnable by anyone who sends its
release ID ([why](/docs/concepts/releases-and-deployments#revoked-releases)).
Revoke it sooner if it is the less secure of the two.

## Limits

- **Both versions share one project's users and sessions.** A user who signs
  up under version B meets version A on their next sign-in if they switch
  versions. Keep changes to a user schema working under both, and keep the
  assignment sticky.
- **Each version keeps the variables of its own newest deployment.** Rotating a
  secret by redeploying one version does not reach the other.
- **Redeploying version B, for example to change a variable, makes it the
  release the origin serves** to everything that does not pin. Deploy version
  A again afterwards.
- **A deploy to `main` during the test** makes a new release, which pinned
  visitors do not get until you rebuild with its ID.
- **Only sign-ins your app starts are split.** An OpenID Connect authorization
  request from another client gets the release the origin serves.
