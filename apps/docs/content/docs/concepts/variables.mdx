---
title: Variables
description: How a project stores values that differ between production and previews, keeps secrets encrypted, and freezes the values with each deployment.
---

A variable is a named value the project stores on the server. Configuration files reference it, so secrets and values that differ between production and previews stay out of `.zitadel/`. The usual case is an identity provider's client ID and secret ([Social sign-in](/docs/guides/social-sign-in)).

## References

A configuration file references a variable as `${{ NAME }}`. Today an identity provider connection's `oidc.client_id` and `oidc.client_secret` take one:

```json
{
  "oidc": {
    "client_id": "${{ GOOGLE_CLIENT_ID }}",
    "client_secret": "${{ GOOGLE_CLIENT_SECRET }}"
  }
}
```

The release holds the reference; the deployment supplies the value. A name uses letters, digits and underscores. A value is a string, number or boolean (`--as number`).

## Secrets

A secret is stored encrypted and can be replaced but never read back. `zitadel variable set NAME --secret` prompts for it or reads standard input, never the command line. A connection's `client_secret` must reference a secret; its `client_id` takes a literal or a plain variable. `zitadel deploy` checks both.

## Primary and preview values

A variable has up to two values, one for [primary origins](/docs/concepts/origins-and-previews#primary-origins) and one for [previews](/docs/concepts/origins-and-previews#preview-patterns-and-previews). Anyone who finds a preview URL can open it, so it must never run with a production secret.

- A plain `zitadel variable set NAME <value>` writes both values.
- `--secret` writes the primary value only and removes the preview one.
- `--preview` writes the preview value only.

Neither falls back to the other. `zitadel variable list` shows primary values and `--preview` the preview ones, with secrets hidden.

## Values are frozen per deployment

A [deployment](/docs/concepts/releases-and-deployments#deployment) copies its target's values when it is created. A changed variable reaches users on the next `zitadel deploy`, which creates a new deployment even when the files are unchanged. A rollback brings back the old values with the old release, and a sign-in in progress keeps the values it started with. `zitadel variable resolve` shows what the live deployment froze.

A deploy that references a name with no value for its target fails with `dep.variables_missing`, listing the names. Set them with `zitadel variable set` (`--preview` for a preview deploy) and deploy again.
