title: Configuration as code
description: How your project's auth configuration lives in repo files, syncs with plan and apply, and becomes revisions.
---

Repo files describe configuration; server APIs own runtime resources. Your project's user schemas, login flows, branding, and sign-in connections live in your repository, where you review them like code, and `zitadel plan` and `zitadel apply` sync them to the platform. [Edit the login flow and schema](/docs/guides/plan-apply) walks through a change.

## What the CLI writes

- `zitadel.json`
- `.zitadel/**`
- framework-specific app files
- `.env.example`, the environment template to commit
- `.env.local`, with the project's real values, including the project secret

## What stays out of source control

Commit `zitadel.json` and `.zitadel/**`, apart from these: `.env.local` and `.zitadel/secret` hold the project secret, and `.zitadel/local/**` is a local server's runtime data, not product configuration. Setup adds `.zitadel/secret` and `.env*` (all but `.env.example`) to `.gitignore`; `start` adds `.zitadel/local/`.

## How syncing works

`zitadel plan` validates local configuration and previews the sync diff without mutating files or platform state. `zitadel apply` validates and uploads it.

- `.zitadel/state.json` maps each config file to its platform id and last-synced content hash. `plan` and `apply` compare against it to decide what changed; don't edit it by hand.
- **Flows are validated at plan time** against the same rules the platform enforces on apply — transition wiring, step reachability, schema field references, and cross-purpose invariants (e.g. a login entry step must wire `user_not_found` when `register` is also a purpose). Violations fail `plan` and `apply` before anything is uploaded, with the same error text the server would return. Non-blocking product guidance shows up as `# warning:` lines in the plan. (If the pre-flight ever disagrees with your server version, set `ZITADEL_SKIP_FLOW_VALIDATION=1` to skip it and let the server decide.)
- **SSO configuration is checked across files at plan time.** `plan` and `apply` read your user schemas, login flows and connection files together and stop, before anything is changed, when they disagree about what the plan touches: a step that offers a provider its schema does not list (or when SSO is off), a schema that lists a provider with no connection file, a step that offers providers without routing every outcome (a `user_already_exists` route that carries an action does not count), a claim mapping that fills nothing the schema defines, a `verified_claims` key with no `claim_mapping` row, or a mapping or `verified_claims` key that names a property no schema has (a top-level property name, not a dotted path, with a "Did you mean" when one is close). It also stops on a mapping that cannot work at sign-in: a standard claim of a type the property cannot hold (such as `updated_at` into a string), a verification that reads a claim that is not a boolean or that vouches for a different claim than the property is filled from, a claim name with a space around it, a `subject_claim` that is a profile claim or an account name, a provider listed twice, a connection field the contract does not define, and a user-creating step that neither asks for a required property nor has every provider map it. Two softer mistakes warn instead of stopping, so `apply` carries on where `plan` only warned: a verification of a property that is not unique in any schema that lists the connection (nothing reads it today), and a custom connection that reads a standard claim without the scope that returns it (a catalog connection, whose scopes the CLI scaffolds, still stops). The files a plan does not touch are not judged again; two connection files may not share a slug or a project variable, and that is checked across all of them. One error names every problem with the file, the step and the name at fault. Setting `ZITADEL_SKIP_FLOW_VALIDATION` turns this check off along with flow validation.
- **A connection's `oidc` block names no endpoint, or every one it needs.** With none, the endpoints come from the issuer's discovery document. Otherwise it names `authorization_endpoint`, `jwks_uri`, `token_endpoint`, and `userinfo_endpoint` unless `id_token_mapping` is true. The server refuses a block in between (`idp.endpoints_partial`), so `plan` and `apply` refuse it first with `E_VALIDATION`, naming the file and the missing endpoints, and an apply never stops part-way. `ZITADEL_SKIP_FLOW_VALIDATION` does not skip this.
- **Connection files are also checked against the platform, and that check is never skipped.** `ZITADEL_SKIP_FLOW_VALIDATION` does not turn these off. When a `client_id` or `client_secret` names a project variable, it must exist (`E_CREDENTIAL_MISSING` when it does not), the id must be a plain variable and the secret a secret one, and one variable may not serve both (`E_VALIDATION`). The `slug`, `protocol`, `oidc.issuer`, and `subject_claim` (an absent one reads as `sub`) of a connection that was applied cannot be edited (`E_VALIDATION`). If the platform cannot be read, the plan stops instead of skipping them.
- **A removed connection file is not deleted.** Deleting a connection is not supported yet, so `plan` and `apply` report the file as kept: separately from the changes, with its own count (`unsupported_deletions` in `--json`, plus the files in `unsupported_deletion_files` on `apply`) and never as "no changes". Renaming a connection file is a move: the file takes over the connection, and nothing is left to restore.
- Schemas and flows are **revisioned**: an edit publishes a new immutable revision instead of mutating the old one. Existing users keep validating against the schema revision they were created with. Older flow revisions stay active; a login that names a flow runs its newest active revision.
- Flows name their schema by its `objectType` in `user_schema` and run against its newest revision, so a schema edit needs no change to `user_schema`. If the edit removes or renames a property a step collects, update that step's `fields`: `plan` only checks the flows it uploads.
- Flow files carry `"$schema": "../meta/flow-definition.json"` — a pointer at the flow dialect spec setup copies into `.zitadel/meta/`, so editors validate and autocomplete flow edits offline. It is local-only: the platform ignores it, and syncing never treats it as a change.
- Your local files stay as written: `apply` never writes what the platform stores back into them. The one exception is a flow whose `user_schema` pins a schema revision id: when `apply` publishes a new revision of that schema, it re-pins the flow to the new id, and lists the file in `files_updated`.
- Comparison is semantic rather than byte-for-byte. The platform stores defaults you leave out: it writes `"x-audit": false` into every schema property that omits it, and `pkce_enabled`, `token_endpoint_auth_method` and `id_token_mapping` into a connection's `oidc` block. A field you leave out reads as its default, so spelling a default out or deleting it again changes no behavior and `plan` reports no change. That holds at any depth, including on a leaf of a nested object property.
- `plan` diffs lists element by element. A flow's steps and a step's actions are matched by `name`, so an edit to one step shows as the lines that changed under that step, and the unchanged steps are summarized as hidden.
