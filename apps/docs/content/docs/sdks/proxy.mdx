---
title: SDK proxy
description: Why framework SDKs proxy Zitadel requests through the app origin.
---

The SDK proxy is a route on your app's own origin, `/__nextgen/*`, that forwards the browser's Zitadel requests to the Zitadel backend. Same-origin means the request goes to the same scheme, host and port as your app's page.

For Next.js, Nuxt, SvelteKit, SolidStart, Qwik Router and TanStack Start, the SDK middleware proxies `/__nextgen/*` requests to the Zitadel backend, validates the session token, and redirects unauthenticated users away from protected routes. Zitadel issues encrypted session tokens, so the middleware checks each one against `GET /sessions/me`.

Only Zitadel's refusal signs a user out. When that check answers `401`, or `404` for a session that is gone, the middleware clears the session cookie. When it gets no answer it can act on (Zitadel answers `5xx`, does not answer in time, or cannot be reached), the middleware keeps the cookie and renders the request signed out, and a protected route answers `503 Service Unavailable` instead of sending a user who may well be signed in to the login page. The next request checks again.

This keeps the app in control of browser-visible routes and cookies while Zitadel remains the backend API.

The default proxy path is:

```text
/__nextgen
```

The login and logout components call the same-origin proxy path by default when configured through the SDK.

## The project secret

Only one call in the browser flow needs a project credential: `POST /sessions/exchange`, which turns a completed sign-in into a session. The other calls need none, or only the session cookie the browser already holds. The proxy adds the project secret (`ZITADEL_PROJECT_SECRET`, which setup writes to `.env.local`) to that call as a bearer token, unless the call already carries an `Authorization` header, and to no other call. The secret stays on the server side of the proxy and never reaches the browser.

The SDKs call the API under `/api/v1`, so a browser call reaches the proxy as `/__nextgen/api/v1/…` and goes on to the server unchanged. Until 1.0.0 the server also answers every operation at its old path, which apps on an earlier SDK still call. So the proxy knows the exchange, and the session calls below, by both paths: `POST /api/v1/sessions/exchange` and `POST /sessions/exchange`.

## Sessions belong to one project

A session belongs to the project it was signed in to, while a browser sends a host's cookies to every app on it: on `localhost`, to every port, including the console of a local runtime. So the server middleware counts a session as signed in only when it belongs to the app's own project. It reads the session with `GET /sessions/me?project_id=…`, which refuses a session of another project with `403 sess.project_mismatch`, and it checks the project the answer names as well. A JWT must name the project in its `aud` claim. The logout components sign out with `DELETE /sessions/me?project_id=…` the same way, so signing out of an app never ends a session of another project. An app's own calls on its signed-in user take the same `project_id`: `GET` and `PATCH /users/me`, and `GET /users/me/projects`, `/users/me/schema`, `/users/me/teams`, `/users/me/passkeys`, `/users/me/identity_links` and `/users/me/password`. Without it, they answer for whichever session the cookie holds.

The project comes from the middleware's `projectId` option, else from `ZITADEL_PROJECT_ID`, which setup writes to `.env.local`, else from the framework's public project id variable. With none, no session counts as signed in. A session of another project reads as signed out, and its cookie stays: it is live in the app it belongs to.

## One session cookie per project

Zitadel sets and reads one session cookie, `__Host-zitadel_session`. Over plain http to a loopback host, such as `http://localhost:8080`, it is `zitadel_session` instead: a browser keeps a cookie with the `__Host-` prefix only when it is `Secure`, and Safari drops a `Secure` cookie there. Under that name alone, the apps and the console on one host would share a single cookie, and each sign-in would sign the others out. So the proxy keeps the app's session in a cookie named after its project, `__Host-zitadel_session_<project id>`, or `zitadel_session_<project id>` when the app is served over plain http to a loopback host. It turns the cookie Zitadel sets into the app's on its way to the browser, with the prefix and `Secure` as the app's own address needs, and sends the app's cookie to Zitadel as `__Host-zitadel_session`. It passes no other project's session cookie on. On `localhost`, signing in to an app leaves the console of a local runtime and every other app signed in.

The `__Host-` prefix keeps other hosts from planting a session cookie: a browser accepts a cookie with it only from the host itself, over https. So where the app is served over https, the proxy and the middleware read no session cookie without the prefix.

On a server without platform bootstrap, the console signs in to the app's project, so on `localhost` the session it keeps under Zitadel's name may be one of the app's. The first time the middleware or the session check of the widgets reads such a session, and it signs in a user of the app's project, it is copied to the app's cookie. Zitadel's cookie keeps it, because the console still uses it. When the user next signs in or out through the app, the proxy clears Zitadel's cookie if it holds a session of the app's project, and on sign-out ends that session too, so it cannot sign the user back in. A session of another project in that cookie stays where it is. A response that sets a session cookie sends `Cache-Control: private, no-store`. With no project configured, the proxy passes the cookies through unchanged.

The session cookies Zitadel used before, `__nextgen_session` and `__nextgen_session_<project id>`, are neither read nor passed on: a browser that held one signs in again.

The dev proxies the CLI writes for single-page apps keep the session the same way, reading the project from `ZITADEL_PROJECT_ID` in `.env.local`. `zitadel doctor --fix` adds this to a dev proxy an earlier setup wrote, and `zitadel doctor` warns until then; it says the hooks must be added by hand to a dev proxy changed since. A dev proxy whose hooks an earlier setup wrote for the `__nextgen_session` cookies fails `zitadel doctor` until `zitadel doctor --fix` replaces them. In production, an SPA's own proxy passes Zitadel's session cookie through, which is fine there: a production host serves one project.

## OAuth issuer and metadata

A project's [OAuth authorization server](/docs/guides/enable-oauth) is reached through the proxy, so its issuer is your app's own address: `{origin}/__nextgen/oauth/{project_id}`, such as `https://app.acme.com/__nextgen/oauth/<project-id>`. An OAuth client checks that the metadata it fetched names the issuer it asked for. So Zitadel must build that same URL from the request the proxy forwarded.

- **The metadata path.** RFC 8414 puts the metadata at `/.well-known/oauth-authorization-server/__nextgen/oauth/{project_id}`, outside the proxy path. The proxy forwards that path to the server's `/.well-known/oauth-authorization-server/oauth/{project_id}`.
- **The proxy's headers.** On every request it forwards, the proxy sets `X-Forwarded-Prefix` to its proxy path and `X-Zitadel-Login-Path` to the path of `loginPath`. It replaces any value the client sent. The server builds the issuer from the forwarded origin and `X-Forwarded-Prefix`. The authorization endpoint sends the user to the login path.
- **Which origins get an issuer.** The server builds an issuer only on one of the project's primary origins, matched exactly. A preview origin, the Zitadel server's own origin, and any other origin `X-Forwarded-Host` claims get none, and the metadata answers `404`.
- **Only the app's own project.** Requests targeting other projects are answered with a `404` by the proxy. It does the same for every project when the app has no project ID configured.
- **Only `/__nextgen`, or no prefix.** The server enforces this: it builds an issuer only when `X-Forwarded-Prefix` is `/__nextgen` or absent, and answers `404` for any other value. The issuer must be the URL the client fetched ([RFC 8414 §3.3](https://www.rfc-editor.org/rfc/rfc8414#section-3.3)), and the header comes from whoever calls the server. So the server builds issuers only at the two paths it knows a client reaches it by. An app that sets another `proxyPath` has no issuer, and its server log says so, as it does when no project ID is configured.

The endpoints a browser visits, such as `authorize`, sit under the issuer and go through the proxy. The ones a client calls from its own server, such as `token` and `jwks`, are on the Zitadel server's public URL: `{zitadel_url}/oauth/{project_id}/…`. No proxy sits in between, and the metadata names both kinds.

On a server with platform bootstrap, the platform project, which the console signs in to, has its own issuer: the Zitadel server's public URL followed by `/oauth`. It answers only there, never through an app.

### Your own proxy

You do not need the SDKs' proxy. A proxy of your own gets an issuer when it forwards to Zitadel in one of these two ways:

- **Under `/__nextgen`, as the SDKs do.** Forward `/__nextgen/*` with that prefix stripped, and map the metadata path above as the SDKs do. Send `X-Forwarded-Prefix: /__nextgen`. The issuer is `{origin}/__nextgen/oauth/{project_id}`.
- **At the origin's root.** Forward `/oauth/{project_id}/*` and `/.well-known/oauth-authorization-server/oauth/{project_id}` unchanged, with no `X-Forwarded-Prefix`. The issuer is `{origin}/oauth/{project_id}`.

Either way, send `X-Forwarded-Host` and `X-Forwarded-Proto` with your app's origin, replacing any value the client sent. Send `X-Zitadel-Login-Path` when your login page is not at `/login`. Forward your own project's OAuth paths only, and answer `404` for any other project's. The server trusts a primary origin's proxy with this, and does not check that no other project lists the same origin.

## OAuth metadata URLs

A client finds an authorization server from its issuer by fetching a metadata document at a well-known URL. The standards place that URL in different ways for an issuer with a path, such as `https://app.acme.com/__nextgen/oauth/<project-id>`. Zitadel serves one of them today.

| Form | Defined by | URL through the app | Who answers |
| --- | --- | --- | --- |
| OAuth metadata, well-known inserted before the issuer's path | [RFC 8414 §3.1](https://www.rfc-editor.org/rfc/rfc8414#section-3.1) | `/.well-known/oauth-authorization-server/__nextgen/oauth/{project_id}` | Zitadel, with the metadata |
| OpenID configuration, well-known appended after the issuer's path | [OpenID Connect Discovery 1.0 §4](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfig) | `/__nextgen/oauth/{project_id}/.well-known/openid-configuration` | Zitadel, with `404` |
| OpenID configuration, well-known inserted before the issuer's path | [RFC 8414 §5](https://www.rfc-editor.org/rfc/rfc8414#section-5) | `/.well-known/openid-configuration/__nextgen/oauth/{project_id}` | Your app: the proxy does not forward it |
| OAuth metadata, well-known appended after the issuer's path | none; some clients try it | `/__nextgen/oauth/{project_id}/.well-known/oauth-authorization-server` | Zitadel, with `404` |
| Well-known at the root, for an issuer without a path | [RFC 8414 §3](https://www.rfc-editor.org/rfc/rfc8414#section-3) | `/.well-known/oauth-authorization-server` | Your app: every project's issuer has a path |

Zitadel serves no OpenID configuration because it issues no ID tokens yet, so it cannot fill the fields OpenID Connect Discovery requires. The SDKs' proxy maps only the RFC 8414 form onto the server. The forms under the proxy path reach Zitadel anyway, which answers them with `404`.

## SPAs in production

Single-page apps (React, Vue, Angular, Solid, Svelte, Qwik) have no server of their own. In local development the CLI scaffolds a dev-server proxy for `/__nextgen/*` that adds the project secret to the session exchange. The CLI scaffolds nothing for production yet. The generated app sends no credential of its own, so in production it needs a same-origin proxy that adds the project secret to the session exchange, and to no other call. Add it only when the browser says the request comes from your own site: the `Sec-Fetch-Site` header is `same-origin`, or, on an older browser that sends no such header, the `Origin` header names your own host. A page on another site can otherwise make a visitor's browser post to the proxy and sign them in as someone else. A plain rewrite cannot do that. The app's packages call `POST /api/v1/sessions/exchange`; have the proxy recognise that path, and `POST /sessions/exchange` for an app on an earlier SDK. A proxy that knows only the old path adds no secret to the exchange, and sign-in fails.

A dev proxy an earlier setup wrote knows only `/sessions/exchange`, so sign-in fails through it. `zitadel doctor` reports it, and `zitadel doctor --fix` moves it to both paths; a dev proxy changed since must be changed by hand.

A planned change will remove the project-secret requirement from this browser-facing path. A browser-safe, origin-checked credential will replace it, with the project's origin allowlist as the enforcement boundary. A plain platform entry will then be enough: a `vercel.json` rewrite, a `netlify.toml` redirect, or a minimal Cloudflare worker (Cloudflare redirects cannot proxy external origins), with no secrets in platform env stores. The credential rollout and CLI scaffolding for these platform configs are tracked in [zitadel/nextgen#560](https://github.com/zitadel/nextgen/issues/560).
