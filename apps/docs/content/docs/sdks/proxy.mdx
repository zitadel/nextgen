---
title: SDK proxy
description: How framework SDKs forward authentication calls to Zitadel through your app's origin, and what the proxy adds.
---

The SDK proxy is the same-origin path `/__nextgen/*` in your app. It forwards your app's authentication calls to Zitadel. Framework SDKs keep this traffic on your app's origin, so the app controls browser-visible routes and cookies while Zitadel stays the API behind them.

For Next.js and Nuxt, the SDK middleware proxies `/__nextgen/*` requests to Zitadel. It also validates the session token and redirects unauthenticated users away from protected routes. Zitadel issues encrypted session tokens, so the middleware checks each one against `GET /sessions/me`.

Only Zitadel's refusal signs a user out. If the check answers `401`, or `404` for a session that is gone, the middleware clears the session cookie. Three other outcomes leave the cookie in place: Zitadel answers `5xx`, does not answer in time, or cannot be reached. The middleware then renders the request signed out. A protected route answers `503 Service Unavailable` instead of sending a user who may be signed in to the login page. The next request checks again.

The default proxy path is:

```text
/__nextgen
```

The login and logout components call this path by default when you configure them through the SDK.

## The project secret

Only one call in the browser flow needs a project credential: `POST /sessions/exchange`, which turns a completed sign-in into a session. The other calls need none, or only the session cookie the browser already holds.

The proxy adds the project secret to that call as a bearer token, unless the call already carries an `Authorization` header. It adds the secret to no other call. The secret is `ZITADEL_PROJECT_SECRET`, which setup writes to `.env.local`. It stays on the server side of the proxy and never reaches the browser.

## Sessions belong to one project

A session belongs to the project it was signed in to. A browser sends a host's cookies to every app on that host. On `localhost`, that means every port, including the console of a local runtime. So the server middleware counts a session as signed in only when it belongs to the app's own project.

The middleware reads the session with `GET /sessions/me?project_id=<project-id>`. Zitadel refuses a session of another project with `403 sess.project_mismatch`. The middleware also checks the project that the answer names. A JWT must name the project in its `aud` claim, the field that says who the token is for.

The logout components sign out with `DELETE /sessions/me?project_id=<project-id>` in the same way. Signing out of one app never ends a session of another project.

An app's own calls on its signed-in user take the same `project_id`:

- `GET` and `PATCH /users/me`
- `GET /users/me/projects`, `/users/me/schema`, `/users/me/teams`, `/users/me/passkeys`, `/users/me/identity_links` and `/users/me/password`

Without it, these calls answer for whichever session the cookie holds.

The project comes from the middleware's `projectId` option. Otherwise it comes from `ZITADEL_PROJECT_ID`, which setup writes to `.env.local`, and then from the framework's public project ID variable. With none of these, no session counts as signed in. A session of another project reads as signed out, and its cookie stays, because it is live in the app it belongs to.

## One session cookie per project

Zitadel sets and reads one session cookie, `__nextgen_session`. If apps used that name alone, the apps and the console on one host would share a single cookie, and each sign-in would sign the others out.

So the proxy keeps the app's session in a cookie named after its project, `__nextgen_session_<project-id>`:

- It renames the cookie Zitadel sets on its way to the browser.
- It sends the app's cookie to Zitadel under Zitadel's name.
- It passes no other project's session cookie on.

On `localhost`, signing in to an app leaves the console of a local runtime and every other app signed in.

A user who signed in before an app moved to this cookie holds the session under `__nextgen_session`. The first time the middleware or the login components' session check reads it, and it signs in a user of the app's project, it is copied to the app's cookie.

The old cookie stays, because on a server without platform bootstrap the console signs in to the app's project and keeps its session there. The next time the user signs in or out through the app, the proxy clears the old cookie if it holds a session of the app's project. On sign-out it also ends that session, so it cannot sign the user back in. A session of another project in that cookie stays where it is.

A response that sets a session cookie sends `Cache-Control: private, no-store`. With no project configured, the proxy passes the cookies through unchanged.

The dev proxies that the CLI writes for single-page apps keep the session the same way. They read the project from `ZITADEL_PROJECT_ID` in `.env.local`. They do not move a session kept under `__nextgen_session`, so a developer who was signed in to an SPA signs in once more after the upgrade.

`zitadel doctor --fix` adds this to a dev proxy that an earlier setup wrote. `zitadel doctor` warns until then. For a dev proxy you changed since, it says you must add the hooks by hand. In production, an SPA's own proxy passes `__nextgen_session` through. That is fine there, because a production host serves one project.

## SPAs in production

Single-page apps (React, Vue, Angular, Solid, Svelte, Qwik) have no server of their own. In local development, the CLI scaffolds a dev-server proxy for `/__nextgen/*` that adds the project secret to the session exchange. The CLI scaffolds nothing for production yet.

The generated app sends no credential of its own. In production it needs a same-origin proxy that adds the project secret to the session exchange, and to no other call. A plain rewrite cannot do that.

A planned change will remove the project-secret requirement from this browser-facing path. A browser-safe credential replaces it, and the project's origin allowlist (the origins the project accepts) is what enforces it. A plain platform entry will then be enough:

- a `vercel.json` rewrite
- a `netlify.toml` redirect
- a minimal Cloudflare worker, because Cloudflare redirects cannot proxy external origins

None of these needs secrets in the platform's environment store. The credential rollout and the CLI scaffolding for these platform configs are tracked in [zitadel/nextgen#560](https://github.com/zitadel/nextgen/issues/560).
