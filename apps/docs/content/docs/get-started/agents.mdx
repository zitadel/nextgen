title: Agent setup
description: Drive the Zitadel CLI with JSON envelopes and prove auth in a browser.
---

The CLI is an agent-facing product surface. Agents should prefer structured JSON over prose hints and should prove the generated app in a browser.

## Invocation contract

Always pass:

```sh
--non-interactive --json
```

When operating outside the current directory, also pass:

```sh
--cwd <path>
```

The CLI prints one parseable JSON object on stdout. Installer, audit, and package-manager progress belongs on stderr. Capture stdout and stderr separately when scripting. The contract covers the Zitadel commands; oclif's built-in `help`, `version`, and `commands` print no envelope.

## Envelope shape

Every JSON envelope includes:

- `cli_version`
- `command`
- `source`
- `status`: `ok`, `skipped`, or `error`

`ok` responses include command-specific `data` and a `warnings` list. `skipped` is a deliberate no-op, not a failure, with a stable `reason` such as `already-claimed`. `error` responses include `code`, `message`, and usually a `hint`. Agents should prefer `next_commands` over prose hints: it sits inside `data` on `ok` responses and at the top level on `skipped` and `error` responses.

## Agent prompt

```text
Create a new, empty local app directory with a lowercase name, such as my-app, and run these in it:

1. npx @zitadel/cli@alpha doctor --non-interactive --json
2. npx @zitadel/cli@alpha start --non-interactive --json
3. npx @zitadel/cli@alpha setup --framework next --server local --non-interactive --json
4. npm run dev

Use the available browser automation to open the generated app. Register a unique user, verify the signed-in profile state, log out, log back in with the same user, and finish on the signed-in page.

To reach the management console, run
npx @zitadel/cli@alpha console --non-interactive --json and open data.sign_in_url
right away. Each link signs in the local admin once and expires after a minute, so
get a new one per visit. The link step 2 returns usually expires before setup finishes.

Summarize commands run, JSON statuses, files changed, browser steps completed, and any setup or UI friction.
```

## Stable UI proof

`<zitadel-login>` and `<zitadel-session>` are web components with shadow DOM, and the fields and buttons inside them have shadow roots of their own. The published components close those roots, so DOM-walking drivers cannot see inside them until the roots are opened: call `openShadowRoots(page)` from `@zitadel/testing/playwright` before the first navigation, or install an init script that makes every `Element.prototype.attachShadow` call attach with `mode: "open"`. Once they are open, drivers with shadow-DOM-aware locators can target the test hooks directly, and generic DOM-eval drivers need to recurse through every shadow root. Drivers that read the browser's accessibility tree see the fields either way.

The hooks are `data-testid` values. Useful ones include:

- `zitadel-field-email` and `zitadel-field-password` (the field elements)
- `zitadel-input-email` and `zitadel-input-password` (the native inputs inside them)
- `zitadel-action-submit` (the submit button element)
- `zitadel-action-submit-button` (the native button inside it)

For sign-out, the generated profile page renders `<zitadel-session>`: target `[data-testid="zitadel-session-logout"]`. An app that renders `<zitadel-logout>` instead, as the React, Vue, Solid, Svelte, and Qwik manual samples do, has no test id there: click its "Open user menu" button, then target the `.signout-btn` button.
