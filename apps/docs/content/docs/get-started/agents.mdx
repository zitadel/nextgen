A coding agent can drive the Zitadel CLI and prove the generated app in a browser. The CLI answers each command with an envelope: one JSON object on stdout with a fixed set of fields. Prefer the envelope over prose hints.

## Agent Skills

The CLI ships an [Agent Skill](https://agentskills.io) so a coding agent can
drive it with always-current guidance. Install it into any skills-compatible
agent (Claude Code, Cursor, Copilot, Codex, and more) from the repo:

```sh
npx skills add zitadel/nextgen --full-depth
```

`--full-depth` installs the whole set — the `zitadel` router skill, the CLI
skill, and the per-framework SDK and component skills. Without it, only the
top-level router skill is installed. The CLI skill also ships inside the
`@zitadel/cli` package.

## Invocation contract

Always pass:

```sh
--non-interactive --json
```

When operating outside the current directory, also pass:

```sh
--cwd <path>
```

The CLI prints one parseable JSON object on stdout. Installer, audit, and package-manager progress goes to stderr. When scripting, capture stdout and stderr separately, into files outside the app directory. Setup scaffolds a new app only into an empty directory. The contract covers the Zitadel commands. The built-in `help`, `version`, and `commands` print no envelope.

## Envelope shape

Every envelope includes:

- `cli_version`
- `command`
- `source`
- `status`: `ok`, `skipped`, or `error`

`ok` responses include command-specific `data` and a `warnings` list.

`skipped` is a deliberate no-op, not a failure. It has a stable `reason`, such as `already-claimed`.

`error` responses include `code`, `message`, and usually a `hint`.

Prefer `next_commands` over prose hints. It sits inside `data` on `ok` responses and at the top level on `skipped` and `error` responses.

## Agent prompt

```text
Create a new, empty local app directory with a lowercase name, such as my-app, and run these in it:

1. npx @zitadel/cli@latest doctor --non-interactive --json
2. npx @zitadel/cli@latest start --non-interactive --json
3. npx @zitadel/cli@latest setup --framework next --server local --non-interactive --json
4. npm run dev

Use the available browser automation to open the generated app. Register a unique user, verify the signed-in profile state, log out, log back in with the same user, and finish on the signed-in page.

To reach the management console, run
npx @zitadel/cli@latest console --non-interactive --json and open data.sign_in_url
right away. Each link signs in the local admin once and expires after a minute, so
get a new one per visit. The link step 2 returns usually expires before setup finishes.

Summarize commands run, JSON statuses, files changed, browser steps completed, and any setup or UI friction.
```

## Stable UI proof

`<zitadel-login>` and `<zitadel-session>` are web components with shadow DOM, an encapsulated DOM tree. The fields and buttons inside them have shadow roots of their own. Browser drivers with shadow-DOM-aware locators can target the test hooks directly. Generic DOM-eval drivers must recurse through every shadow root.

The hooks are `data-testid` values. Useful ones are:

- `zitadel-field-email` and `zitadel-field-password` (the field elements)
- `zitadel-input-email` and `zitadel-input-password` (the native inputs inside them)
- `zitadel-action-submit` (the submit button element)
- `zitadel-action-submit-button` (the native button inside it)

To sign out, target `[data-testid="zitadel-session-logout"]`: the generated profile page renders `<zitadel-session>`. An app that renders `<zitadel-logout>` instead has no test ID there. The React, Vue, Solid, Svelte, and Qwik manual samples do this. Click its "Open user menu" button, then target the `.signout-btn` button.
